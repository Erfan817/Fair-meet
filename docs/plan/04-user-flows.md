# FairMeet 用户流程文档

> 归属：FairMeet 完整出行规划产品 · 阶段 A（产品与工程基线）交付物之一
> 依据：[实施任务书](../deepseek-harness-implementation-brief.md)（重点 §3 端到端流程、§4 末段地点库/行程能力按需调用、§6 阶段 A、§9 完成标准）
> 背景材料：旧规格 [phase0-spec.md](../phase0-spec.md)（多人公平会面点推荐）、[review-2026-09-21.md](../review-2026-09-21.md)
> 性质：描述**用户视角**的端到端主链路、状态与降级、验收剧本与权限隐私。本文不定义实现细节，也不改变产品主线。

---

## 0. 文档定位与主线声明

FairMeet 的产品主线是**完整出行规划**：把成员分散的灵感、个人需求和现实约束，整理成有来源、可讨论、可执行、并能随变化局部调整的**共享旅程计划**。

一切子能力（餐厅推荐、多人约饭、会面点推荐、路线计算、地点发现）都在"一趟旅程"的框架内按需调用，**不是产品定位，也不是独立 MVP**。本文件描述的主链路永远从"一趟旅程"出发，会面点/餐厅只作为旅程中的见面、用餐、集合场景出现。

术语约定：

| 术语 | 含义 |
|------|------|
| 旅程（Trip） | 一次多人出行的共享计划本体，含基本信息、成员、权限、状态、逐日行程 |
| 成员（Member） | 受邀加入某趟旅程的同行者，拥有对该旅程的授权访问 |
| 灵感（Inspiration） | 成员放入的链接 / 地点 / 攻略文字 / 手动记录，等待抽取与核实 |
| 硬约束 / 偏好 / 可协商项 | 三类需求强度：不可让步、希望满足、可以谈 |
| 行程条目（Plan Item） | 逐日计划中的一项安排：日期时间、活动、地点、停留、交通段、费用、来源、状态 |
| 地点（Place） | 地点库中的规范地点或分店，带坐标、类别、外部来源映射 |
| 核实状态 | 已识别 / 待确认 / 已核实 / 解析失败 / 已排除 |

每条流程统一用 6 个维度描述：**触发 → 系统行为 → AI 行为 → 成员决策点 → 产物 → 失败/降级路径**。

## 1. 端到端主链路分步流程

以下 8 步与任务书 §3.1–3.8 一一对应。

### 3.1 创建旅程

- **触发**：发起人用自然语言（"十一想去成都，我、小李和爸妈一起去，人均预算 3000"）或表单描述目的地、日期、同行者、预算、旅行偏好。
- **系统行为**：
  - 建立可持续编辑的**旅程草案**，持久化基本信息与发起人对该旅程的权限。
  - 提供字段结构化视图（目的地、日期区间、成员名单、预算、偏好标签），每个字段可检查、可修改。
  - 生成邀请入口（分享链接的容器，具体邀请在 3.2）。
- **AI 行为**：
  - 解析自然语言并抽取已知字段，明确标出"这是我从你的描述里提取的"。
  - 对影响规划的关键缺项追问（如日期未定、预算口径不清、同行者人数不明），一次问最有价值的少数几项，不堆砌问题。
  - 提取结果必须交用户确认或修改，不得直接当作既定事实向下推进。
- **成员决策点**：发起人确认 / 修正提取到的字段；决定旅程名称与大致意图。
- **产物**：旅程草案（含结构化基本信息），处于"草案"状态。
- **失败/降级路径**：
  - AI 抽取不全或抽错：发起人手改表单字段即可，旅程草案照常建立。
  - AI 不可用：可直接走纯表单创建，主流程不阻塞。

### 3.2 邀请同行者与收集需求

- **触发**：发起人通过分享链接邀请成员；成员打开链接加入。
- **系统行为**：
  - 生成可分享的邀请链接，落实**成员访问权限**（成员仅能进入被授权的这趟旅程）。
  - 为每位成员提供需求录入：出发地、可参加日期、预算、兴趣、饮食需求、行动/无障碍需求。
  - 每项需求**必须标注**为硬约束 / 偏好 / 可协商项。
  - 展示**加入状态、未回应项、待补充信息**（谁还没填、谁填了但缺关键项）。
- **AI 行为**：
  - 帮助成员把口语化描述（"我肠胃不好，别太辣，走路别太多"）整理成结构化需求，并请其确认"饮食限制"和"行动限制"各属哪一档强度。
  - 提醒发起人哪些成员的未回应项会影响后续协调。
- **成员决策点**：每位成员确认自己需求的强度归类（尤其是硬约束）；发起人决定是否催办未回应成员、是否接受缺项先推进。
- **产物**：带强度标注的成员需求集合 + 成员状态看板（已加入 / 未回应 / 待补充）。
- **失败/降级路径**：
  - 成员无法或不愿用结构化表单：允许仅填文字，由 AI 整理后回填并请其确认。
  - 部分成员迟迟未回应：旅程可带"待补充"标记继续推进，系统显式保留该缺口并在 3.4 提示。
  - 越权访问：非授权成员通过链接访问时按权限拒绝，不得读取旅程数据。

### 3.3 收集灵感与来源

- **触发**：任一成员把链接、地点、攻略文字或手动记录放入旅程"灵感箱"。
- **系统行为**：
  - 尝试抽取地点、活动、时间建议与**来源**。
  - 做去重、分类，并尽量匹配到地点库中的**具体地点/分店**。
  - 每个灵感维护状态：已识别 / 待确认 / 已核实 / 解析失败 / 已排除。
  - 保留来源与获取时间，供后续核实。
- **AI 行为**：
  - 抽取候选地点与活动，标注哪些是原文明确写的、哪些是推断。
  - 对匹配到多个分店或名称含糊的灵感提出待确认，而非擅自定一个。
- **成员决策点**：成员确认或手动修正识别结果（改地点、改分店、标为已排除）；判断某条灵感是否保留。
- **产物**：带来源、核实状态、分类的灵感清单；已确认项可进入 3.5 方案生成。
- **失败/降级路径**（关键）：
  - **链接解析失败**（社交/点评平台不稳定）：状态标为"解析失败"，提供**手动补充/修正**入口（手动填地点、活动、时间），**不阻塞规划**。
  - 抽取到模糊地点：标为"待确认"，等成员澄清，不阻塞其他已识别项。
  - 外部解析服务整体不可用：灵感箱仍可手动添加地点，主流程继续（阶段 B 即要求无外部解析也能跑）。
  - 无法验证的内容不得伪装成"已核实"，只能停留在"已识别/待确认"。

### 3.4 汇总约束与发现冲突

- **触发**：成员需求与灵感积累到一定量后，进入汇总协调（发起人或系统提示触发）。
- **系统行为**：
  - 汇总日期、预算、成员偏好、出发地与硬约束。
  - 提示可识别的问题：**日期冲突、预算超限、地点过多、行动需求不匹配**等。
  - 区分硬约束 / 偏好 / 可协商项：硬约束冲突必须**显式报告并请成员处理**，**不得自动放宽硬约束**。
- **AI 行为**：
  - 总结"待讨论问题清单"，为每个冲突给出可选处理方向（如改日期、拆分组、换住宿区域）。
  - 解释冲突来源（哪几位成员的哪些需求相撞），不得静默忽略或径直给出"已协调好"的结论。
- **成员决策点**：成员决定如何处理每个冲突（让步某条偏好、拆分活动、更换日期、升级为需要全体确认的议题）。
- **产物**：冲突/缺失信息清单 + 待讨论议题列表（带关联成员与需求）。
- **失败/降级路径**：
  - 硬约束无法调和：显式报告并停留在此状态，请成员介入，**不生成掩盖冲突的方案**。
  - 信息不足（如预算口径不明）：标注缺口，向相关成员追问，避免用假设值硬算。
  - AI 判断失误：冲突清单可被成员修正或标注"误报"，系统据此更新。

### 3.5 形成并比较方案

- **触发**：冲突有初步处理方向后，发起人请求生成方案。
- **系统行为**：
  - 基于灵感、约束、地点与路线数据，产生一个或多个**可比较方案**。
  - 方案差异可体现在目的地安排、住宿区域、每日主题、活动密度、预算或交通方式。
  - 每个方案展示：**依据、预算估算、交通影响、主要取舍、未核实信息**；明确区分已核实 / 外部数据 / 估算 / 未知。
- **AI 行为**：
  - 组织方案结构并解释取舍（"方案 A 更省交通时间但住宿贵；方案 B 预算低但每天多约 40 分钟在途"）。
  - 标注哪些数字来自地图/规则服务、哪些是估算、哪些未知，**不凭空给精确数字**。
- **成员决策点**：成员比较并表达倾向（评论、投票、收藏偏好方案）；决定是否采纳某个方案、做微调或重新生成。
- **产物**：一或多份带依据、估算与来源标注的可比较方案。
- **失败/降级路径**：
  - 路线/预算数据不可用：方案以"估算"呈现，并注明缺失的数据源，**不伪造精确值**。
  - 只够生成一个方案：明确说明为何无法给出对比项，不制造虚假多样性。
  - 方案触及硬约束：直接标红并说明，不允许以"方案很诱人"为由绕过硬约束。

### 3.6 共同编辑逐日行程

- **触发**：选定方案骨架后，成员进入共享逐日行程共同编辑。
- **系统行为**：
  - 提供按天组织的共享计划；行程条目表达**日期/时间、活动、地点、预计停留、交通段、费用估算、来源、确认状态**。
  - **地图与时间线关联**：点条目看地图，点地图看条目。
  - 支持评论、收藏备选、投票、提出替换、确认。
  - 餐厅、集合点、会面地点都以**普通行程条目**形式出现（详见第 3 节转化说明）。
- **AI 行为**：
  - 把成员的自然语言修改请求转成**受控修改提案**（"帮我把第三天下午改成室内活动"→ 具体条目替换提案）。
  - 对已确认内容的修改**只提案不直改**，并说明影响范围。
- **成员决策点**：成员确认/否决每条提案；决定条目去留、顺序、替换备选。
- **产物**：可协作、可编辑的逐日行程（含状态与来源）。
- **失败/降级路径**：
  - 地图服务不可用：时间线视图仍可编辑，地图标注"暂不可用"。
  - 并发编辑冲突：以版本/变更记录提示，需成员确认后再合并，不静默覆盖。

### 3.7 检查可执行性

- **触发**：行程成型后（每轮编辑后或发起人手动触发）执行检查。
- **系统行为**：
  - 检查时间安排、地点间交通、营业时间（若数据可用）、预算、行程密度、明显绕行。
  - 数据必须**区分已核实 / 外部数据 / 估算 / 未知**。
  - 路线与数值必须来自地图/规则服务或明确标为估算，**不能由 LLM 凭空给精确数字**。
- **AI 行为**：
  - 解释检查发现的问题及严重程度（硬冲突 vs 仅提醒），给出可选修复方向。
  - 不越权修改；把修复作为提案交给成员。
- **成员决策点**：成员处理被报告的问题（调整时间、换地点、降密度、接受风险并标注）。
- **产物**：可执行性检查报告（问题清单 + 数据状态 + 修复提案）。
- **失败/降级路径**：
  - 营业时间等外部数据缺失：标"未知"，不臆造，提示成员自行核实。
  - 路线服务不可用：交通时间标"估算/不可用"，检查基于可用数据给出**有限结论**并说明局限。
  - 关键数据全缺时：明确"无法完成完整校验"，只报确定项，不装作已通过。

### 3.8 确认、出发前查看与途中调整

- **触发**：成员确认计划；临近出发查看摘要；旅途中就地调整。
- **系统行为**：
  - 计划项支持状态机：草案 / 待讨论 / 待确认 / 已确认 / 已完成 / 已取消/替换。
  - 修改已确认内容时，**展示差异及受影响的路线、预算、后续安排**，用户确认后才更新；保存变更历史。
  - 提供出发前摘要（可分享/可执行视图）。
  - 旅途中可针对某天或局部重排，**尽量保留不受影响的已确认项**。
- **AI 行为**：
  - 生成变更影响说明（"推迟第二天午餐会让下午两个已确认景点顺延、打车费 +约 30 元"）。
  - 途中按成员新情况给局部重排提案，默认保护其他已确认项不受波及。
- **成员决策点**：逐条确认/否决变更；确认局部重排范围；决定是否接受影响。
- **产物**：确认后的行程 + 变更历史 + 出发前摘要；途中重排后的受影响局部计划。
- **失败/降级路径**：
  - 突发的实时数据（临时闭馆、天气）不可得：显式标"无法核实"，交由成员判断。
  - 变更引发连锁影响：完整列出受影响项，成员可只接受部分、其余保持原样。
  - 通信/协作不可用：至少保证本人只读查看已确认计划与摘要，不丢状态。

## 2. 用户可见状态与降级一览

用户在每个环节应看到**明确的状态**，任何"做不到"都要有可见的降级，而不是静默失败。

| 场景 | 用户可见状态 | 降级方式 |
|------|--------------|----------|
| 链接/攻略解析失败 | 灵感状态"解析失败" | 提供手动补充/修正入口，不阻塞规划 |
| 识别结果不确定 | "待确认" | 成员确认或改正后才进入方案 |
| 外部数据不可用（路线/营业/价格） | "估算 / 未知 / 数据暂不可用" | 以估算标注呈现，注明缺失来源，不伪造精确值 |
| 地图服务不可用 | 地图区域显示"暂不可用" | 时间线与条目仍可编辑查看 |
| 硬约束冲突 | 显式冲突报告 + 关联成员 | 请成员处理，AI 不放宽、不掩盖 |
| AI 不可用 | 功能降级提示 | 可用纯表单/手动编辑继续主流程 |
| 并发编辑冲突 | 版本/差异提示 | 成员确认后合并，不静默覆盖 |
| 数据无法核实 | "无法核实" | 交由成员判断，不标为已核实 |

原则：**任何外部依赖失败都有手动路径**；**任何不确定都显式标注**；**任何硬约束冲突都上报给成员而非自动消解**。

## 3. 旧会面点推荐能力 → 旅程内可复用能力的转化说明

### 3.1 转化结论（对应任务书 §4 末段、§6 阶段 A）

旧产品逻辑链：`地址 → 地理编码 → 公平中心 → POI 搜索 → 评分排序 → 地图展示`（见 phase0-spec.md / review-2026-09-21.md）。

新定位下，这条链**不再是产品主线**，而是**旅程内"选择会面点 / 集合点 / 餐厅分店"的工具**，通过**地点库 + 行程能力按需调用**接入，不形成与旅程割裂的独立流程。

一句话：**它从"产品本人"降为"旅程里的一个选点工具"。**

### 3.2 能力拆分与接入点

| 旧能力 | 在旅程中的新角色 | 接入方式 | 出现在哪些流程步骤 |
|--------|------------------|----------|----------------------|
| 地理编码 | 把成员出发地/灵感地址规范化为坐标，写入地点库 | 地点库规范化能力，供 3.2 出发地、3.3 灵感匹配、3.7 交通检查调用 | 3.2 / 3.3 / 3.7 |
| 公平中心 | 计算"对大家相对公平"的会面/集合区域 | 选点时的一个参考信号（如"这一带对三人都比较均衡"），**不是产品出口** | 3.5 / 3.6 |
| POI 搜索 | 在候选区域内找餐厅分店、咖啡馆、集合场所 | 作为行程条目的候选地点来源，落入地点库 | 3.5 / 3.6 |
| 多因子评分（含分数明细） | 对候选分店/集合点排序并解释理由 | 作为条目提案的排序与依据，保留可解释性 | 3.5 / 3.6 |
| 地图展示 | 在旅程地图上标注地点、条目与路线 | 复用为旅程地图的组成部分 | 3.6 / 3.7 / 3.8 |

### 3.3 典型旅程内用法（示例，非独立流程）

1. 3.6 中某天安排了"大家从各自住处出发、一起吃饭"：成员选"选个集合点/餐厅分店"，系统调用公平中心 + POI + 评分，给出若干候选并解释理由，**选中项成为一条普通行程条目**（带地点、状态、来源）。
2. 3.5 方案比较时，住宿区域附近的餐饮分店可通过 POI 搜索纳入某方案，参与预算与密度比较。
3. 3.7 检查时，会面/集合点的交通段使用地理编码与路线数据校验可达性。

### 3.4 必须坚守的边界

- **不再是产品定位**：不会出现"只有一个会面点推荐页"这种脱离旅程的入口；会面点/餐厅永远是某趟旅程里的条目或某一步的候选。
- **按需调用**：只有旅程走到需要"见面/用餐/集合"的场景时才触发，不作为创建旅程的起点。
- **不割裂**：选点结果直接写入地点库与行程条目，与成员需求、约束、地图、确认状态处于同一旅程空间，不另起一套孤立的推荐 UI。
- **保留可解释性**：旧产品的"分数明细"优势保留为条目的排序依据，继续服务于"为什么选这个点"的解释。

## 5. 权限与隐私

对应任务书 §2、§8 与 §10 的隐私风险项。

### 5.1 访问授权

- **成员仅能访问被授权的旅程**：邀请链接即授权边界；非成员访问被拒绝，不得读取旅程任何数据。
- 旅程空间内的数据按旅程隔离，一个旅程的成员不能看到另一个旅程。
- 发起人对成员管理与分享链接的创建/失效负责；成员退出后失去后续访问，已产生内容的可见策略明确。
- 权限校验在业务服务层执行，**AI 不得绕过权限**、不得直接写数据库，只能通过受校验的业务操作提案。

### 5.2 最小化收集

- 仅收集规划必需的信息：出发地（可粗到区域而非精确门牌）、可参加日期、预算区间、兴趣、饮食需求、行动/无障碍需求。
- **位置**：出发地用于计算交通与会面点，尽量使用"区域/地铁站"级别，不强制精确住址。
- **饮食/健康**：饮食禁忌与行动需求属于**敏感信息**，仅用于本旅程的约束校验与选点，不作为营销或跨旅程用途；按其强度（硬约束/偏好）区别对待，硬约束才在必要范围内向相关成员可见。
- **行动/无障碍需求**：以"约束"形式参与校验，展示给需要协调的成员时以解决问题为限，避免在公开视图暴露个人健康细节。
- 成员可只填必要项，非必要字段默认可留空。

### 5.3 删除与数据生命周期

- 成员可请求退出旅程并删除其个人提交（需求、灵感中的个人信息），删除行为明确可预期。
- 发起人可删除/归档整个旅程；删除后其共享内容不再对新访问可见。
- 外部数据的来源与获取时间随内容存储，当外部服务不可用或数据过期，明确降级并允许成员处理。
- 日志不得泄露密钥或无关敏感信息；AI 修改提案、用户确认与数据来源需留痕以便审计与恢复，但留痕内容遵循最小化原则。
