# 个人 Agent 时代的定位与路线图

> 日期：2026-11-12
> 性质：**产品定位与后续路线规划**，不改变 A–E 已实现范围，不引入新的已确认承诺。
> 结论先行：FairMeet 不与个人 agent 争夺「替一个人排行程」，而是成为**多人行程的共识账本与决策基础设施**——对外表现为一个跟着群聊走的「旅程房间」：人用免登录链接、agent 用受委托工具，读写同一份不可私改的账本，最终确认权属于人。

## 1. 问题

个人 agent（有长期记忆、能直接订票查资料、能连续对话的单用户助手）正在吞掉「AI 帮我做个攻略」这件事。如果 FairMeet 的叙事停留在「AI 排行程」，那么用户没有理由打开一个网页、创建旅程、拉人进来——个人 agent 免费、更快、更顺手。

但多人出行真正难的部分不在生成：

- 有人想去博物馆，有人必须周日返程，两个硬约束同时成立时该牺牲谁；
- 谁在什么时候把已经确认的安排悄悄改了；
- AI 给出的营业时间、票价、路线，到底有没有出处；
- 三个人的 agent 各自给出方案，凭什么接受其中一个。

这些是**多主体协调问题**，单用户 agent 在结构上无法独立承担。本文件给出 FairMeet 在这个前提下的定位、产品形态、接口方向和分阶段路线。

## 2. 判断与前提

### 2.1 会被商品化的能力

| 能力 | 现状 | 个人 agent 到来后 |
| --- | --- | --- |
| 目的地资料检索 | FairMeet 已在做（受来源限制） | 成为助手标配，不再构成差异 |
| 逐日行程生成 | AI 提案 | 助手直接给，用户不会为此换工具 |
| 预算估算、冲突识别 | 确定性规则 | 助手可内置同类规则，但缺多方输入 |
| 单次重排 | 局部重排 | 助手可完成，且不需要版本记录 |

### 2.2 不会被商品化的能力

- **多主体状态的权威副本**：每个人表达过的硬约束、偏好、可协商项，必须有一个各方都认可的存放处。
- **中立裁决**：冲突与预算超支的判定不能由当事某一方的助手执行。
- **变更留痕与确认**：谁提议、谁确认、改了什么、影响哪些已确认安排。
- **来源与不确定性**：估算、外部数据、未知必须可区分，且不能被某个 agent 的自信语气覆盖。

### 2.3 时间窗口

Agent 互操作协议（MCP、A2A 等）仍在演进，没有事实标准。此时先把自己的领域语义（提案、确认、约束、来源）映射成机器可调用的接口，比等到协议定型后再适配成本更低。**谁先定义了「多人行程的共识操作」，谁就更容易被其他 agent 当作底层。**

### 2.4 失败条件（诚实列出）

以下任一情况成立，FairMeet 就会被个人 agent 取代，规划再详细也没有意义：

1. 产品最终只服务单个用户，多人协作退化为「邀请链接 + 一个人替所有人排」；
2. AI 生成质量成为唯一卖点，而共识、留痕、来源这些能力被砍掉；
3. 接口封闭，成员自己的 agent 无法参与，用户必须在「用助手」和「用 FairMeet」之间二选一。

## 3. 定位重述

### 3.1 旧叙事与新叙事

| | 旧叙事 | 新叙事 |
| --- | --- | --- |
| 产品是谁 | AI 协助的多人出行规划应用 | 多人行程的共识与决策基础设施 |
| 用户为什么来 | 让 AI 帮忙排行程 | 让几个人真正达成并守住同一个安排 |
| AI 的角色 | 主要功能 | 众多参与者之一（可能是每个人自己的 agent） |
| 竞争对象 | 其他行程 App | 不需要竞争：成为它们调用的那一层 |
| 成功标志 | 生成出好看的行程 | 冲突被看见、决定被确认、变更可追溯 |

一句话：**不同的人（和他们的 agent）在同一份账本上提案、核对、确认；FairMeet 不替谁做决定，但让决定可达成、可核对、可追溯。**

### 3.2 价值分层

按不可替代程度从高到低排列，后续投入按此顺序保护：

1. **留痕层**：提案、确认、版本快照、变更历史、审计主体。
2. **裁决层**：硬约束检查、预算汇总、冲突识别、来源等级。
3. **记录层**：成员需求、灵感、地点库、逐日安排。
4. **生成层**：检索、抽取、行程草案、局部重排。

生成层可以外包给任何模型或个人 agent；前三层必须留在 FairMeet 内，否则产品失去存在理由。

### 3.3 明确不做

- 不做通用个人助手，不与用户已有的 agent 抢入口；
- 不做内容社区、攻略平台、点评聚合；
- 不做预订、支付、票务交易；
- 不承诺「AI 全自动排好」——确认权始终在人。

## 4. 产品形态：旅程房间

先拆掉一个隐含前提：**被取代的是「生成一份计划」，不是「让几个人对同一份安排做出承诺」。** 一次旅行不是文档，是一组带钱、时间与他人约定的承诺。个人 agent 只能代表一个承诺方——它能替你说「我想去博物馆」，但不能替另外两个人点头，也不能在有人私自改动已确认安排时做出裁决。形态应由「必须存在中立第三方」的位置决定，而不是由「能生成什么」决定。

### 4.1 一句话形态

**FairMeet 不做「你要打开的应用」，做「你们群里那份谁都不能私自改掉的安排」。**

「旅程房间（Trip Room）」是一个有稳定身份的共享对象，四个面同时朝外：

| 面朝谁 | 形态 | 作用 |
| --- | --- | --- |
| 成员本人 | 一条链接，免注册 | 看安排、提需求、点确认 |
| 成员的 agent | 一组工具（MCP + 委托令牌） | 读上下文、提交需求与提案 |
| 群聊 | 可回传的提案/确认卡片 | 决定发生在人们本来就在的地方 |
| 所有人 | 一份账本 | 需求、灵感、提案、确认、版本、来源 |

关键点：**界面是可替换的，账本不是。** 今天用网页，明天成员用他自己的助手，后天群里发一张卡片——变的只是投影，写入永远走「提案 → 差异 → 确认 → 留痕」。个人 agent 越强，接入 FairMeet 的人越多，而不是把它换掉。

### 4.2 三层形态与演进顺序

三层叠加存在，不是互相替代：

1. **参考客户端 + 账本（现有 Web）**：不是最终形态，但必须有——它是确认入口，也是外部相信这套语义的样板。
2. **工具层（MCP + 委托授权）**：让外部 agent 能读能提，确认权仍留在人。
3. **原生场景（群聊卡片 / 机器人）**：把参与动作搬到微信、Slack、Discord 等群聊里，做到「不打开 FairMeet 也能参与」。

顺序不能反：第 3 层依赖第 1 层的确认语义和第 2 层的身份模型，而第 2 层单独做没有分发。**先做 1+2，再谈 3。**

### 4.3 不做的形态

| 形态 | 为什么不行 |
| --- | --- |
| 更强的 AI 行程规划 App | 生成能力正在商品化，正面竞争必输 |
| 攻略 / 点评内容社区 | 内容由各家 agent 抓取，平台接口不可依赖 |
| 通用个人助手 | 打不过用户已经在用的那一个 |
| 纯协议 / SDK | 价值判断对，但没有分发；很少有人为协议专门写客户端 |
| 预订交易平台 | 完全另一场游戏（资质、资金、售后） |

### 4.4 架构含义

账本是核心，UI 是投影。所有写入都是一条带主体（人还是哪个 agent）、带依据、带版本的事件；页面、API、群聊卡片、MCP 都只是对同一份账本的读写视图。

由此得到一条清晰的决策标准：**改界面不伤产品，改确认语义才伤产品。**

「旅行中」是这个形态最锋利的时刻：计划赶不上变化，几个人同时改，谁的信息最新、谁改了什么——个人 agent 在这种多方并发下天然失灵。出发前的规划只是入口，途中的变更才是账本真正不可替代的场景。

### 4.5 形态是否正确的判定

四个信号，直接对应第 8 节的指标：

- **被绕过率**：群里的决定有多少最终没回到账本上确认（最关键）；
- **参与转化率**：收到链接的人里有多少完成了需求表达或确认；
- **agent 写入占比**：由委托接口产生的写入比例，代表「被调用」是否成立；
- **账本一致性**：已确认安排被静默修改的次数，必须为 0。

## 5. 三条战略支柱

### 5.1 被调用：成为 agent 的工具，而不是对手

把现有领域 API 整理成 agent 可直接使用的接口面，原则是**能力对齐、语义显式、失败可解释**。

需要补的工程能力：

- **委托身份**：区分「人」和「代表某人的 agent」。agent 的每次写入标注 `acting_member` 与 `agent_id`，可在授权页撤销。
- **作用域授权**：读旅程、提交需求、添加灵感、提交提案、查看校验结果分别授权；敏感个人需求默认不向 agent 暴露。
- **提案只能提议**：agent 可以创建提案、补充依据、查看影响，但**不能自行确认**。确认动作必须来自成员本人（见 5.3 的例外条款）。
- **幂等与并发**：写接口支持 `idempotency_key`；修改类提案携带 `expected_revision`，版本冲突时返回明确错误而不是静默覆盖。
- **机器可读错误**：错误码区分「权限不足」「结构非法」「约束冲突」「版本过期」「来源未核实」，便于 agent 自行纠正而不是重试轰炸。

接口形态建议（详细工具清单见 §7 F 阶段）：

```text
REST（现有）  /api/trips/{id}/...            人用的网页与脚本
委托令牌      /api/agent/authorize            成员授权某个 agent
MCP 适配层    fairmeet/mcp/                   把领域操作映射为工具
事件订阅      /api/trips/{id}/events          SSE / webhook，告知「有人改了」
```

### 5.2 降低门槛：参与不需要安装任何东西

个人 agent 时代的竞争点是**谁能让不装 App 的人也参与确认**。现状的邀请链接已经是优势，继续强化：

- 链接即参与：打开链接即可查看旅程、表达需求、确认提案，无需注册。
- 渐进式身份：先以「临时成员」参与；需要长期协作时再绑定身份。
- 确认动作最小化：一键确认 / 拒绝 / 附一句理由；不做多步表单。
- 未来可选：通过 IM 或邮件卡片完成「查看差异 + 确认」，成员不必打开网页。

衡量指标：从收到链接到完成一次有效表达（需求、灵感、确认）的时间与完成率。

### 5.3 守住账本：哪些事不能委托

| 事项 | 能否由 agent 代办 | 说明 |
| --- | --- | --- |
| 提交灵感、地点、公开资料 | 可以 | 必须保留来源，未核实标未知 |
| 起草提案、计算影响 | 可以 | 只能进入待确认状态 |
| 声明成员的硬约束 | 不可以 | 必须成员本人确认；agent 只能「建议补充」 |
| 确认 / 拒绝提案 | 默认不可以 | 除非成员显式开启限定范围的自动确认（见下） |
| 修改已确认安排 | 不可以静默进行 | 必须走提案 + 差异展示 |
| 读取其他成员的敏感需求 | 不可以 | 作用域隔离，按需最小披露 |

**自动确认的例外条款**（可选，默认关闭）：成员可授权「仅限预算上限内、仅限本人条目、仅限无硬约束冲突」的提案自动生效；任何越界条件都退回人工确认。该项在 G 阶段之前只做设计，不实现。

### 5.4 与个人 agent 的四种关系

| 场景 | 表现 | 应对 |
| --- | --- | --- |
| A · 忽略 | 用户直接用个人 agent 排完出发 | 接受流失；服务好必须多人协作的场景 |
| B · 调用 | 成员 agent 通过接口提交需求、提案、确认 | **主目标**：成为默认底层 |
| C · 协商 | 多个 agent 互相交换方案 | 长期机会：提供中立账本与提案交换格式 |
| D · 封闭 | 平台自带 agent 只在自己的生态闭环 | 差异化在开放、可审计、可自托管 |

## 6. 技术方案草案（不改变现有架构）

### 6.1 身份与委托

```text
Member            人；确认权的唯一来源
AgentPrincipal    被授权的代理（外部 agent 或内置助手）
Delegation        member_id + agent_id + scopes + expires_at + revoked_at
AuditEntry        delegation_id + action + proposal_id + revision + created_at
```

原则：`Delegation` 是显式、可撤销、有期限的；任何写入都能反查到「哪个 agent 代表谁」。

### 6.2 接口面复用

优先复用现有领域模块，不新造一套：

| 能力 | 复用模块 | 需要新增 |
| --- | --- | --- |
| 成员需求 | `services.py` | agent 提交时标注来源与「待本人确认」状态 |
| 灵感与地点 | `services.py` / `content/` | 来源等级与抓取时间必填 |
| 提案与确认 | `ai/proposal.py` | 幂等键、`expected_revision`、确认人校验 |
| 约束与预算 | `checks.py` | 返回机器可读的冲突码 |
| 变更与版本 | `history.py` | 审计主体（人 / agent / 委托 id） |
| 局部重排 | `replan.py` | 与提案流程统一入口 |

### 6.3 提案协议机器可读化

现有提案是给人看的待确认对象；agent 场景需要结构化补充：

- `proposal_id`、`base_revision`、`operations[]`（沿用白名单）、`preconditions[]`
- `impact`：受影响条目、预算变化、硬约束冲突、来源缺口
- `status` 状态机：`draft → proposed → confirmed / rejected → applied / superseded`
- 确认必须携带确认人身份；agent 身份调用确认接口一律返回 `confirmation_requires_member`

### 6.4 事件与订阅

成员 A 的 agent 需要知道成员 B 改了行程。首版用轮询 + `revision` 比较即可；后续加 SSE，事件只广播「什么变了」和版本号，不推送他人敏感需求。

### 6.5 非功能与隐私

- 限流与配额：按成员、按 agent、按日；公开搜索沿用现有每日上限。
- 审计留存：agent 行为至少保留到旅程结束后的可配置期限。
- 最小披露：agent 只拿到授权范围内的数据；他人硬约束仅以「是否存在冲突」的形式暴露。
- 密钥：agent 自身密钥不进入 FairMeet 存储；委托令牌可撤销、可轮换。

## 7. 分阶段路线图（F–H）

> 与 A–E 一致：每阶段先设计、再实现、再验收；未通过验收不进入下一阶段。以下阶段不承诺日期。

### F · 被调用（只读 + 低风险写入）— ✅ 已实现（2026-11-12）

> 实现与用法见 [Agent 接入说明](agent-access.md)。核心模块：`fairmeet/agent.py`、`fairmeet/agent_routes.py`、`fairmeet/mcp/`。

- **范围**：MCP 适配层（只读旅程上下文、查询校验结果）；委托令牌；agent 提交需求与灵感（标注来源，硬约束标「待本人确认」）；机器可读错误码。
- **DoD**：
  - 外部 agent 通过 MCP 读取成员可见范围内的旅程上下文；
  - 提交灵感后来源与时间完整，未核实项在页面标未知；
  - agent 无法声明硬约束、无法确认提案（接口返回明确错误码）；
  - 委托可撤销，撤销后立即失效；
  - 全部新增路径有回归测试，模拟网络，不消耗第三方配额。

  以上 DoD 由 `tests/test_agent_api.py` 与 `tests/test_mcp.py` 覆盖（含真实 uvicorn 服务上的 MCP stdio 走查）。

### G · 受控写入（提案 + 审计）— ✅ 已实现（2026-11-12）

> 实现与用法见 [Agent 接入说明](agent-access.md) §4「提案与并发控制」「自动确认」。

- **范围**：agent 创建/补充提案；`expected_revision` 并发控制；确认人校验；审计记录；可选的限定范围自动确认（默认关闭）。
- **DoD**：
  - agent 提交的提案进入待确认列表，带完整影响与差异；
  - 版本过期返回冲突码，不覆盖他人改动；
  - 确认动作只接受成员身份；自动确认的所有越界情形均退回人工；
  - 审计可回答「谁（哪个 agent 代表谁）在何时改了什么」。

  以上 DoD 由 `tests/test_agent_proposals.py` 覆盖；自动确认按「只追加、限额内、无硬约束、版本未变」实现，任一越界都退回人工。

### H · 原生场景与多方协商

- **范围**：群聊卡片 / 机器人入口（可回传的提案与确认卡片，首版不依赖开放平台 API 也能通过链接卡片完成）；提案交换格式（可导出/导入，供多个 agent 之间比较）；事件订阅；跨旅程的可复用成员偏好（严格 opt-in）；自托管说明。
- **DoD**：
  - 成员在群聊中完成一次「查看差异 + 确认」，无需注册并打开完整网页；
  - 两个 agent 可基于同一份旅程上下文各自提交提案，成员并列查看影响；
  - 事件通知在无刷新情况下可用（SSE 首版）；
  - 不出让确认权、不引入未经来源核对的外部事实。

### 明确不在 F–H 内

多 agent 自动谈判并自动达成协议、平台内 IM、预订支付、自动读取第三方平台完整评论。

## 8. 衡量指标

| 指标 | 含义 | 目标方向 |
| --- | --- | --- |
| 被绕过率 | 群内决定最终未回到账本确认的比例 | 下降（最关键） |
| 参与转化率 | 收到邀请链接后完成一次有效表达的比例 | 上升 |
| 确认时延 | 提案产生到有人确认/拒绝的中位时间 | 下降 |
| agent 提交占比 | 经由委托接口提交的需求/灵感/提案比例 | 上升 |
| 提案接受率 | 已确认 / 已处理提案 | 稳定或上升 |
| 冲突拦截 | 被规则拦下的硬约束与预算问题数 | 不作为 KPI，但需可观测 |
| 账本一致性 | 已确认安排被非法静默修改的次数 | **必须为 0** |

## 9. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| agent 代填需求失真 | 错误的「硬约束」锁死行程 | 硬约束必须本人确认；agent 提交仅作建议 |
| 用户被劝离平台 | 个人 agent 直接接管全流程 | 强化邀请链接与免注册确认；提供导出让别人带走结果 |
| 自动确认被滥用 | 误改已确认安排 | 默认关闭；范围、限额、冲突条件三重约束；全程审计 |
| 协议标准变化 | 适配层返工 | 领域语义与传输层分离，MCP 只做薄适配 |
| 群聊平台能力受限 | 机器人或卡片不可用、账号有风险 | 先做「链接卡片」这类不依赖平台 API 的形态，机器人后置 |
| 隐私泄露 | 成员敏感需求流向他人 agent | 作用域 + 最小披露；他人约束只暴露冲突存在性 |
| 生成质量不足以支撑叙事 | 用户仍觉得不好用 | 把生成交给可替换的模型；产品承诺放在共识与留痕 |

## 10. 待确认事项

以下问题需要产品侧明确后再进入 F 阶段实现：

1. ~~**优先形态**：先做 MCP 适配层，还是先做委托令牌 + REST？~~ 已按建议落地（F 阶段）：委托令牌 + REST 为主，MCP 作为薄适配层。
2. **自动确认**：是否允许任何形式的自动确认？若允许，限额与范围如何界定？
3. **托管模式**：是否提供公开托管实例，还是以自托管 + 邀请链接为主？
4. **提案交换**：H 阶段的导出格式是否要兼容外部协议，还是先自定义最小格式？
5. **审计留存**：默认保留多久？旅程结束后是否对成员可见？
6. **群聊入口**：首版原生场景优先接入哪个平台？（考虑平台开放能力、账号风险与目标用户实际使用的 IM。）
