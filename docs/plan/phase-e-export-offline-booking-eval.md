# 阶段 E · 导出 / 离线 / 外部预订整合评估

> 依据：任务书 §6 阶段 E「根据实际反馈再评估导出、离线或外部预订整合」、§2.8「订票、支付、订单履约不属于核心范围，可外链或预留接口」。
> 本文**只做评估，不实现**（不擅自引入交易系统）。结论供决策参考。

---

## 1. 导出（Export）

| 维度 | 评估 |
|------|------|
| 需求来源 | 出发前摘要已能 `GET /api/trips/{id}/summary` 返回结构化 JSON；成员常想「存到手机/发群里」。 |
| 低成本方案 | 服务端渲染的 `/trip/{id}/summary` 页面支持浏览器「打印/另存为 PDF」即可满足「适合分享/执行」的最小诉求，**零额外依赖**。 |
| 中等方案 | 生成 .ics 日历（每日条目带时间）+ PDF（reportlab/weasyprint）。优点：可导入手机日历；缺点：新增依赖、时间不精确时误导。 |
| 建议 | **先不加依赖**：保留 summary 页面 + JSON API 作为导出基础；若用户反馈需要 .ics/PDF，再作为独立小任务实现，并在生成物上标明「估算/未核实」项。 |
| 风险 | 导出物若含估算费用/未核实营业时间，需在文件内标注来源状态，避免被当作事实。 |

## 2. 离线（Offline）

| 维度 | 评估 |
|------|------|
| 需求来源 | 途中网络不稳时查看当天安排。 |
| 低成本方案 | 移动端页面用 Service Worker 缓存 `/trip/{id}/ontrip` 的 HTML 与静态资源，离线可读最近一次加载的行程（只读）。 |
| 阻力 | 写操作需服务端；离线只能只读。加入 PWA 清单与缓存会增加前端复杂度与版本失效问题。 |
| 建议 | 当前**不实现离线**；沿用「普通请求/刷新」，网络不稳时由浏览器常规缓存兜底。若实测途中确实常断网，再评估只读 Service Worker 缓存（不改数据模型）。 |
| 与任务书一致 | §10「实时协作可先用普通请求/刷新验证流程，确认需要后再采用」——离线同理，先按需。 |

## 3. 外部预订整合（Booking）

| 维度 | 评估 |
|------|------|
| 明确边界 | 任务书 §2.8：**订票、支付、订单履约不属于核心范围**，只可外链或预留接口。 |
| 低成本方案 | 行程条目/景点旁展示「在地图/平台搜索该地点」的外链（不携带交易，不做订单）；或不加。 |
| 不建议 | 接入真实订单/支付 API：涉及合规、资金、账号安全，远超本产品主线，且任务书明确排除。 |
| 建议 | **不实现任何交易能力**。如需，仅在 UI 加只读外链（跳转到用户自己的平台），不保存订单、不处理支付。 |

## 4. 结论

| 能力 | 决策 | 触发再评估的条件 |
|------|------|------------------|
| 导出 | 暂只用 summary 页 + JSON API（+浏览器打印） | 用户反馈需要 .ics/PDF 分享 |
| 离线 | 暂不实现 | 实测途中经常断网，且只读缓存即可满足 |
| 外部预订 | 不实现交易；如需要仅外链 | 用户明确要求且能接受合规/资金风险（当前不做） |

> 以上均为评估结论，阶段 E **未实现**任何导出文件生成、离线缓存或预订/支付；后续如要做，应作为独立任务在用户确认后单独立项。
