# 先检索、后规划：功能设计草案

> 日期：2026-11-11。
> 状态：**供评审的新增功能设计，未实现、未进行平台接入实测**。本次仅整理设计，不代表用户已批准编码、付费调用或平台登录。
> 适用：FairMeet 现有 FastAPI + Jinja2 + SQLite + DeepSeek 架构，首轮仍为成都 3–5 人、2–3 天国内游。
> 约束：沿用 [已确认决策](07-confirmed-decisions.md)；自动解析仍须先验证合法性与稳定性，不以本文改写历史决策。

## 1. 产品目标

让助手在推荐地点、安排旅程前，主动查找与这趟旅行有关的攻略、点评及官方信息，把资料整理成**有依据、能解释取舍、仍由成员确认**的行程建议。

这不是另做一个点评聚合网站。检索服务于完整旅行规划：找玩法、筛候选、发现风险，再结合同行者需求、预算、位置与时间安排。

**一句话体验：开启联网检索后，告诉助手想怎么玩，它先查资料，再解释为什么这样安排。**

### 成功标准

- 推荐理由能追溯到本轮真实取得的资料，而不是模型自行编造来源。
- 能区分“攻略作者的体验”“外部服务返回的数据”“已核实事实”“估算或未知”。
- 同名门店、过期信息、平台不可用不会被悄悄忽略。
- 搜索不自动改变灵感、地点库或行程；采纳仍走明确操作与提案确认。
- 关闭联网或遇到平台限制时，原有手动规划仍可使用。

## 3. 首版范围

### 3.1 必须包含

1. 在 AI 协调助手内提供“先查资料再规划”入口；按旅程、请求成员记录联网选择。
2. 把目的地、活动区域和偏好转换为有限数量的检索任务。
3. 通过至少一个**经过单独验收的真实只读来源**搜索、读取公开或已获授权的信息。
4. 输出 3–5 个候选（不足时如实给出），展示来源、取舍、风险与待确认项。
5. 对地点做城市/分店消歧；仅对有可靠位置的候选计算路线。
6. 提供“保存为灵感”“据此生成行程提案”；确认前不写入行程。
7. 显示检索进度、取消、部分成功与失败降级；离线 Fake 模式可复现演示。

**真实检索上线门槛：至少一个来源完成授权/规则审查与搜索、读取实测。** 未达门槛时只能交付标明“模拟资料”的演示，不得宣传已能联网查点评。

### 3.2 不纳入首版

- 承诺同时稳定接通小红书、大众点评、美团，或读取完整评论。
- 支付、订餐、预订、发帖、评论、点赞、收藏到第三方账号。
- 代替用户登录、收集密码/Cookie、自动处理验证码或绕过访问限制。
- 图片/视频内容理解、评论全量抓取、跨旅程个人画像。
- 后台定时全网搜索、自动监视商家变化、自动改写已确认行程。
- 多 Agent 框架、向量数据库、Redis、分布式任务队列或新的前端构建链。

### 3.3 来源接入顺序

| 来源 | 用途 | 首版策略与边界 |
|---|---|---|
| 经验证的通用网页搜索/读取服务 | 发现公开攻略、官方页面及平台可见信息 | 优先候选；需另选服务、核对费用/使用条款/可访问范围，不默认已有搜索 API |
| 景区、场馆、商家的官方信息 | 开放时间、预约条件、票务规则 | 关键事实优先；取得页面后仍需判断适用日期、分店和票种 |
| 高德 | POI、位置与路线核对 | 复用现有端口；不默认具有营业、评分、人均或实时排队数据 |
| 小红书只读工具 | 玩法、探店体验、近期风险反馈 | 可选增强；先验证授权、登录、运行环境和稳定性，不作为主流程唯一依赖 |
| 大众点评、美团 | 店铺详情、消费参考、用户体验 | 本轮没有验证可直接使用的只读接口；可尝试允许访问的公开页面，失败则保留链接与手动补充 |

来源不可用时，不伪造对应平台的评分、人均、评论或“交叉验证”标签。GitHub 项目有相关代码，也不等于取得平台数据使用授权。

## 4. 用户流程与界面

### 4.1 开启与触发

入口沿用“AI 协调助手”，不增加独立产品首页。

- 开发环境与新成员默认关闭联网。首次开启时说明：检索词会发往启用的数据源，可能产生已配置范围内的费用。
- 联网选择按 `trip_id + member_id` 隔离；一个成员的选择不能替其他成员授权。关闭后新请求不联网，运行中任务发出取消信号。
- 服务端可禁用某来源或设成本上限；没有配置/没有授权的来源不得调用。
- 成员开启后，对适合的请求自动检索，不必每轮再问“要不要搜”；扩大费用范围、更换需新授权的服务或要求登录时另行确认。

| 请求 | 行为 |
|---|---|
| “成都三天，想吃本地菜、少排队，帮我们安排” | 先检索，再生成候选与提案；日期等必要条件缺失时先澄清 |
| “第二天午餐附近有什么适合五个人的店？” | 仅检索相应区域和餐饮需求，不重做整趟计划 |
| “这家店值得加入吗？”或粘贴攻略链接 | 定点读取/检索，再与当前路线和需求比较 |
| “检查预算冲突”“把备注改短一点” | 不联网，使用已有数据；不得仅因出现“检查”二字跳过真正需要检索的请求 |
| “只用我们收藏的资料规划” | 不联网；注明哪些资料只有链接、哪些已有正文/人工摘要 |
| “更新一下这家店的营业信息” | 明确刷新相关事实，不自动修改现有行程 |

目的地是地点检索的必需信息。单纯发现玩法不强制先填写出行日期；缺日期时不判断某日是否开放，也不生成依赖该日期的确定安排。

### 4.2 检索过程

在助手回复区展示阶段，而不是不停输出工具日志：

`准备检索 → 查找资料 → 核对地点与限制 → 整理建议 → 等待采纳`

同时显示“已读取 X 条正文、Y 条仅有摘要、Z 个来源不可用”。进度不是精确百分比，不声称读完平台全部内容。用户可取消；超时后保留已取得的有效结果。

### 4.3 候选卡片

每张卡片包含：

- 地点/分店、所属区域、是否完成地图匹配。
- 为什么适合这趟旅程：对应哪些成员偏好，哪些需求仍未证实。
- 正面体验与负面反馈，注明是作者观点而非商家事实。
- 价格/时长的口径、适用人数与来源状态；没有数据则显示未知。
- 原始来源链接、内容发布日期（未知则明示）、本次读取时间、取得范围。
- “保存为灵感”“用于生成提案”“本次不考虑”“查看依据”。

示例仅描述交互，不代表真实商家数据：

> **示例川菜馆 · A 分店**（虚构）
> 适合的理由：靠近第二天下午的活动区域，有资料提到多人聚餐。
> 注意：部分作者提到周末等位；“适合五人”尚未向商家确认。
> 费用：未知，不计作 0 元。地址：地图已匹配；营业时间：待核实。
> 依据：正文 2 条、仅摘要 1 条；查看各条来源与日期。

### 4.4 从候选到计划

1. 搜索结果暂存在本次研究批次中，不自动新增灵感或地点。
2. 点击“保存为灵感”是用户明确的保存动作，走成员授权与现有业务服务；来源证据随记录关联，状态不自动变为 verified。预览需说明是否同时保存已消歧地点；未消歧的资料可保存为不关联地点的灵感。
3. “用于生成提案”先显示预览，再由现有提案流程确认。暂不增加另一套行程执行入口。
4. 当前操作契约要求 `day_id/place_id` 引用真实对象，不能在同一提案中猜测新建对象的 ID。首版分两步：先保存/确认所需地点或天数，再基于实际 ID 生成条目提案。研究候选的地点保存由服务端专用选择流程完成：复用同一旅程内已匹配的 Place，或在用户明确确认保存后以现有 PlaceCreate 写入分店名、GCJ-02 坐标和来源，并新增 place_id → 候选/POI ID/地址/字段证据关联；不能只调用现有仅含 name/category 的 OpAddPlace 就宣称位置已保存。
   - 现有 add_inspiration 会按 place_name 另建地点，不能直接用它再生成第二个无坐标 Place。实施时需为灵感输入与服务补充可选 place_id（与 place_name 互斥，校验旅程归属），并在业务服务的事务中完成地点、灵感和研究关联的幂等保存；普通手动导入保持兼容。
   - 坐标只能来自服务端已匹配的候选/地理服务，不能采信模型填入的值；存在真实 place_id 也不代表位置已消歧或全部事实已核实。
5. 已有计划只改指定范围；范围外已确认项保持不动。若受影响，明确展示差异与原因。
6. 沿用现有“提案发起者确认”机制，不宣称实现全体投票或所有成员一致同意。
7. 执行可能部分成功：显示已执行、跳过与失败，不把提案状态 confirmed 当作全部写入成功。

## 5. 检索与筛选规则

### 5.1 有限检索，而非无限浏览

以“成都三天、五人、少排队”为例，构造“目的地/区域 + 需求”检索词，再定点补查候选；不把整段聊天历史直接交给搜索服务。

建议初始预算如下，属于**待实测调优的上限，不是速度承诺**：

| 项目 | 单次研究上限 |
|---|---|
| 搜索请求 | 所有来源合计 4 次 |
| 详情读取 | 6 次；每次尝试都计入，失败不返还预算 |
| 地理/路线调用 | 合计 8 次；只查入围候选及必要交通段，不做全量两两路线矩阵 |
| 模型调用 | 最多 2 次（如需结构化拆解 + 汇总），无自由工具循环 |
| 时间 | 检索阶段最多 60 秒，整个研究最多 120 秒；适配器超时不超过剩余额度 |
| 结果 | 通常 3–5 个候选，不足不凑数 |

查询、读取、重定向与重试都受全局计数和时间预算约束。429、登录失效、验证码、平台封锁立即停止该来源本轮请求，不换账号或后端重试；临时网络错误最多一次重试，也必须仍在预算内。

不具备价格/配额信息的付费来源默认禁用，先配置费用上限。重复点击复用同一个运行任务，不额外触发付费请求。达到限制时优先返回已有证据，不通过不断追加请求“凑齐”报告。

### 5.2 地点消歧与去重

- 使用城市、区域、地址、分店名与平台 POI ID 共同匹配；名称相同不等于同一家店。
- 地图匹配也有失败/歧义状态；歧义未解除不关联坐标，不计算精确通勤。
- 同一笔记转载、同一商家素材、多平台共用评论记录不能计为多个独立证据。
- 大众点评与美团同源内容不因域名不同就算“双重核实”。
- 发布日期和读取日期分别保存；刚读取的旧攻略仍可能过期。

### 5.3 硬约束优先，再解释偏好取舍

筛选顺序：**硬约束 → 时间/路线可行性 → 已知预算 → 多人偏好覆盖 → 证据质量与新近性**。

- 硬约束三态：满足、不满足、未知。不满足则排除；未知不得当作满足。
- 对过敏、无障碍等关键需求，缺少明确依据的候选只能待核实，不进入标为“可执行”的主方案。缺少负面评论不能证明安全。
- 价格未知不当作免费；仅有区间时列区间和估算依据，并披露预算不完整。
- 平台评分分别保留尺度、数量和日期，不把 4.8/5 与 9.0/10 直接平均；不自造“全网综合评分”。
- 点赞、收藏、提及频率仅帮助发现候选，不证明质量，也不等于多位独立用户推荐。
- 首版采用可解释排序与成员偏好覆盖清单，不引入未经校准的“公平指数”。偏好无法兼得时给取舍与备选，不擅自删除某位成员的要求。

## 6. 证据与核实模型

### 6.1 四个维度必须分开

| 维度 | 示例 | 表达含义 |
|---|---|---|
| 来源类型 | 官方、地图、社区、商家、人工补充、模拟 | 信息来自哪里，不代表真假 |
| 取得范围 | 正文、摘要、链接而已、部分评论 | 实际读到了什么，不把摘要冒充全文 |
| 内容性质 | 事实主张、个人体验、估算 | “周末排了 40 分钟”是该作者的一次体验，不是实时排队值 |
| 核实状态 | 外部数据、已核实、估算、未知、冲突 | 当前能作出多强的判断 |

保留 `ProvenanceKind` 的 verified/external/estimated/unknown 语义。冲突、过期、取得范围用独立字段表达，不把它们硬塞进来源枚举，也不将整条 Inspiration 的核实状态当作每个字段都已核实。

### 6.2 建议记录（概念模型，尚无数据库迁移）

| 对象 | 关键字段 |
|---|---|
| `ResearchRun` | id、trip_id、requested_by、intent、scope、输入指纹、授权范围版本、status、各阶段进度、请求/时间预算、started_at、finished_at、error_code、保留截止时间 |
| `SourceDocument` | id、run_id、provider、platform、允许展示的 canonical_url、title、published_at（可空）、fetched_at、content_scope、内容指纹、独立来源分组、可选受限摘录、expires_at |
| `EvidenceClaim` | id、document_id、candidate_id、field、value、unit、applicability、claim_type、证据定位/允许保存的摘录、provenance_kind、verification_method、verified_by、verified_at、冲突组、时效标记 |
| `ResearchCandidate` | id、run_id、名称/分店/区域、匹配的真实 place_id（可空）、匹配状态、相关 evidence_ids、约束检查、推荐/排除理由、决策状态 |
| `ResearchSelection` | run_id、candidate_id、member_id、save/dismiss/build_proposal、实际 inspiration_id/proposal_id、操作时间；用于去重和审计 |
| `EvidenceLink` | trip_id、run_id、claim_id、目标类型/目标 ID（Place/Inspiration/Proposal/Item）、提案操作序号（可空）；绑定分店/位置依据以及提案与条目的具体字段证据 |

原则：

- ID 由服务端分配，模型只能引用授权研究批次中的真实 ID。
- 每个事实字段关联证据，不接受一个页面链接“承包”该店所有结论。
- `external` 只表示外部来源返回，不自动升级为 verified。
- verified 只能来自可审计的核实步骤：人工确认记录，或指定字段的权威来源核查规则（主体、日期、适用条件均匹配）。规则与核实方法留档；模型不能决定核实状态。
- 多篇攻略相互一致最多显示“多源一致”，不能单凭篇数标为 verified；存在相反信息时保留冲突，不投票抹平。
- 证据过期只改变“当前可依赖性”，不抹除当时取得的记录，也不自动改变行程。

### 6.3 模型输出与展示

检索结果作为不可信资料与系统规则隔离传入。模型输出建议附 `candidate_id/evidence_ids`；服务端验证范围、字段与适用条件后才生成来源卡片。

现有 `SourceRef` 可兼容保留，但本轮推荐的“已读取/已核实”标签、URL 和日期只能由服务端证据记录生成，不能直接采用模型写出的 label/kind/detail。非法引用安全拒绝或删除该结论并提示证据不足，不让无依据结论通过展示。

提案与条目通过新增关联记录保存依据，不在现有白名单操作中偷塞未定义字段。旧提案没有证据关联时显示“无本轮检索依据”，不回填伪造来源。

## 7. 服务流程与任务生命周期

### 7.1 编排边界

```text
成员请求 + 本次联网选择
  → 授权与外发数据裁剪
  → 结构化意图/确定性触发判断
  → ResearchService（预算、时间、取消）
      → ContentPort.search / read（只读）
      → 地点消歧与必要的 GeoAdapter 调用
      → 规范化证据、冲突与约束检查
  → 给模型受限的证据上下文，输出候选/说明
  → 服务端校验引用与可行性
  → 返回研究结果
  → 用户选择保存或生成现有 Proposal
  → 用户确认后才执行行程变更
```

首版先用固定阶段编排，不让模型任意拼接工具或执行脚本。来源适配器不得拿到旅程写入工具、数据库执行权限或完整聊天历史。

### 7.2 状态与故障

- 状态：`queued → running → succeeded / partial / failed / cancelled / interrupted`。
- 缺少必要信息在创建任务前返回澄清问题，不启动联网；空搜索结果与请求失败分别记录。
- `succeeded` 表示任务按范围完成，不表示所有商家事实都已核实；部分来源失败、预算耗尽或关键资料不足时为 `partial`。
- 取消为协作式：立即停止新请求，尽可能取消在途调用；已发出的第三方请求和费用不保证撤回。保留已取得结果供查看，取消后不再生成或执行提案。
- 进程重启使未完成任务标为 `interrupted`，不自动重放可能计费的请求；用户可显式重新发起。
- 没有模型时可返回确定性的来源与候选列表，明确“尚未生成 AI 行程”；不假装 FakeLLM 完成真实规划。

### 7.3 轻量执行与复用

- SQLite 保存任务和阶段结果；应用进程内受限 worker 执行，页面用普通请求轮询状态，不引入 WebSocket 或外部队列。
- 初始每进程最多 2 个 worker，每趟旅程最多 1 个活动研究；按成员/旅程限频，设置有界排队。多进程部署时须先用 SQLite 原子领取/租约及全局配额约束，不能把进程内计数误当成全局上限。
- 同一请求以 `trip_id + member_id + idempotency_key` 去重，相同 key 不同请求体拒绝；重复创建不触发第二次联网。保存/采纳动作也必须幂等。
- 复用仅限同一旅程、同一授权范围、相同输入与来源版本下的未过期结果；不跨旅程共享用户摘要、偏好或研究缓存。
- 新鲜度按字段配置：票价、营业与预约等时效数据应更短；没有已验证策略前不自动复用此类字段。每次复用明确显示原读取时间，不称为“刚刚查询”。
- 只复用已经合法保存的资料；复用前重新检查权限、资料保留期限与来源使用条件。

## 8. 提案一致性与安全边界

### 8.1 研究不等于修改权限

所有创建、读取、取消、保存、生成提案及确认入口都必须重新检查当前成员资格与 trip_id 归属，不能凭研究 ID 或成员 ID 字符串直接访问其他旅程。

研究输入指纹至少覆盖日期、预算、参与成员需求、检索范围、受影响行程、来源配置与联网授权范围。资料本身可保存，但生成提案前重新读取当前上下文：

- 日期/预算/范围变化：结果显示“基于旧条件”，要求重新评估，不直接沿用旧可行性结论。
- 成员退出或关闭联网：停止未发出的外部调用，不扩大现有数据可见范围。
- 确认时重新计算相关旅程上下文指纹（日期、预算、当前成员需求、授权范围），并检查触及条目与目标天安排的基线、关键证据有效性。新增条目也必须检查目标天的条目集合/时间/费用，避免别人新增安排后仍沿用旧可行性结论；相关变化时阻止旧提案执行并要求重新生成。
- 执行仍调用现有服务与约束检查，不能靠研究阶段的校验替代执行期授权。

新增检查只针对本功能相关流程逐步落地，不在设计交付中声称既有提案已具备乐观并发或事务批量执行。

### 8.2 外链读取与内容隔离

- 仅允许 http/https，生产优先 https；阻断 localhost、私网/链路本地/元数据地址、非标准目标及不允许的端口，拒绝带用户信息的 URL。
- 域名/能力白名单由服务端配置，不能由模型扩充。DNS 解析、实际连接地址及每次重定向都校验，防止 SSRF 和 DNS 重绑定。
- 限制重定向次数、响应大小、内容类型、读取时长；不执行来源页面脚本，不接受任意下载或本地文件路径。
- 来源正文中的“忽略指令、调用工具、泄露密钥”等内容一律视为资料，不赋予执行权；证据字段也经过 schema 与长度校验。
- 来源文字作为文本转义渲染，不信任原始 HTML；外链限制协议并使用安全的新窗口属性。
- 浏览器/MCP 如需单独服务，由隔离适配器管理，仅导出获准只读工具。不得因工具自称只读就相信其无副作用。

### 8.3 隐私、凭据与保留

- 搜索只外发目的地、必要区域与泛化需求；不发送姓名、member_id、邀请链接、精确出发住址、完整旅程或聊天记录。
- 饮食/无障碍等可能敏感的需求优先本地筛选；确实需要外发时，预览泛化检索词并取得该次明确同意。不因旅程内一人开启联网就上传其他成员敏感需求。
- 密钥只在环境变量/密钥设施；登录凭据留在独立来源服务，不进入旅程库、模型上下文或日志。不替用户登录，不要求粘贴 Cookie。
- 来源 URL 中的访问令牌/签名不得进入展示与日志；仅保存安全规范化链接，访问所需临时凭据由适配器短期管理。无法安全形成公开链接时明示“需在平台内查看”，不伪造可用链接。
- 默认不存整页正文。许可允许时仅保存支持结论所需的最小摘录，建议每文档最多 1000 字符；不允许留存则只存引用和允许的元信息，也不得违反条款进行模型处理。
- 未采纳的研究正文/摘录建议 7 天清理；任务元数据建议 30 天清理。被采纳的依据只保留许可允许的最小审计快照，沿用旅程删除生命周期；若来源期限更短，按更短期限清理并保留“证据已移除”标记。
- 删除旅程时清理其研究、证据关联及本地缓存；日志不得残留原始正文、敏感检索词或凭据。外部服务已接收的数据无法由本地删除保证撤回，开启联网时需说明。

## 9. 接口与代码落点建议

以下均为**拟新增**，不是当前可调用 API；所有路径都带成员授权且执行上节的旅程作用域检查。

| 接口 | 作用 |
|---|---|
| `POST /api/trips/{trip_id}/research` | body 包含 message、intent（discover/plan/check_place）、scope、enabled_sources、consent_version、idempotency_key；只接受已配置来源。缺条件返回澄清；创建成功 202 + run_id |
| `GET /api/trips/{trip_id}/research/{run_id}` | 任务状态、阶段、候选、证据、来源错误、预算消耗和过期提示；不返回凭据/整页原文 |
| `POST /api/trips/{trip_id}/research/{run_id}/cancel` | 幂等取消；已结束任务返回当前状态 |
| `POST /api/trips/{trip_id}/research/{run_id}/selections` | 选择候选并 save/dismiss/build_proposal；重复请求不重复写入，返回实际对象 ID 或待确认提案 |
| `GET /api/trips/{trip_id}/research-sources` | 返回当前成员可用的来源及 search/read 能力、配置/登录/限制状态；不能泄露其他账号会话 |

已有 `/ai/chat` 保留兼容路径；开启检索且符合触发条件时返回受控的 research_pending + run_id，由页面取结果。普通聊天仍沿用现有响应；前端与 API 测试必须覆盖两种形态，不能直接更改同步返回而让旧界面失效。

| 位置 | 建议职责 |
|---|---|
| 拟新增 `fairmeet/content/ports.py` | ContentPort 的 search/read、能力与错误契约，返回规范化文档 |
| 拟新增 `fairmeet/content/models.py` | 研究任务、文档、字段级证据、候选及选择的 Pydantic 模型 |
| 拟新增 `fairmeet/content/service.py` | 有限编排、预算、进度、取消、去重与证据规则；不直接执行行程写入 |
| 拟新增 `fairmeet/content/providers/` | Fake、首个验收通过的真实来源；小红书等按验证结果另加 |
| `fairmeet/ai/orchestrator.py`、`contracts.py` | 触发路由、受限证据上下文、引用校验；保留现有 LLMClient 与 DeepSeek |
| `fairmeet/ai/proposal.py`、`tools.py` | 提案证据关联、基线/过期检查；确认后复用既有业务操作 |
| `fairmeet/domain.py`、`services.py` | 灵感支持同旅程真实 place_id；选择保存复用 PlaceCreate，并事务化保存地点、灵感与研究关联，保留分店坐标及依据 |

SourceRegistry 可保留地理服务台账；内容来源新增分能力与请求作用域的状态，不能用全局 available 布尔值代表所有成员都可访问。具体迁移方案在编码前结合实际表结构细化。

## 10. 验收标准

所有示例资料在离线测试中注明合成，不使用真实个人旅程或登录凭据。

| 编号 | 场景 | 通过条件 |
|---|---|---|
| AC-01 | 关闭联网/普通冲突解释 | 搜索、详情读取调用均为 0；原有规划可用 |
| AC-02 | 开启联网后请求地点推荐 | 在预算内自动搜索并整理候选；无需每轮重复授权，未产生行程写入 |
| AC-03 | 条件缺失 | 地点/必要日期等先澄清；不自行假定城市或用未知日期宣称开放 |
| AC-04 | 仅搜索摘要/仅粘贴链接 | 明确取得范围；不声称读过正文或全部评论，不生成无依据精确价格 |
| AC-05 | 同名异地/不同分店 | 不合并不同实体；未消歧不计算精确路线 |
| AC-06 | 转载、同源平台内容 | 去重或标为同源，不能提高独立证据数量 |
| AC-07 | 过期/冲突事实 | 保留适用日期与分歧，不能直接标为 verified；关键限制未确认不进入可执行主线 |
| AC-08 | 硬约束不满足或未知 | 不满足则排除；关键条件未知则待核实，绝不写成满足 |
| AC-09 | 伪造 evidence_id/verified | 服务端拒绝非法引用与升级，不能在来源卡片中展示为可信依据 |
| AC-10 | 超时、空结果、限流、需登录 | 区分原因；保留部分结果、停止受限来源，不循环重试或换账号 |
| AC-11 | 保存/采纳 | 明确点击才写灵感；行程提案确认前条目数/内容不变；重复点击无重复对象 |
| AC-12 | 新地点/新天数 | 使用两步确认/保存得到真实 ID；分店、坐标与依据关联保留，灵感不重复创建无坐标地点；不让模型编造 day_id/place_id |
| AC-13 | 上下文变化/部分执行 | 提案生成后修改日期/预算/成员需求，或在目标天新增/更改安排，确认时阻止旧提案；执行期仍校验，实际失败/跳过项可见 |
| AC-14 | 取消/进程重启 | 取消后不继续发新请求或提案；中断不自动重放计费请求 |
| AC-15 | 权限、SSRF、注入、XSS | 跨旅程/退出成员被拒；私网/危险重定向不可读，恶意正文不能调用工具或执行脚本 |
| AC-16 | 外发与数据清理 | 请求不含敏感身份/完整上下文；保留期限、旅程删除与日志脱敏生效 |
| AC-17 | 兼容/模拟模式 | 旧聊天与提案流程回归通过；Fake 资料始终有模拟标记，不冒充实时查询 |
| AC-18 | 真实来源上线门禁 | 经同意的真实搜索与读取各有验收记录，说明条款、取得范围、运行环境、费用与失败案例；离线 mock 通过不能代替此项 |

测试分层：纯规则/模型单测、适配器离线 mock、API 授权与幂等、完整 Fake 流程、浏览器交互与移动端、独立的真实来源冒烟。真实联网/付费验收须另获同意，不进入默认 CI。

## 11. 实施顺序与交付门槛

| 小步 | 交付 | 门槛 |
|---|---|---|
| R0 · 来源验证 | 确定首个可用来源、允许用途、费用、授权/登录与实际取得范围 | 用真实成功/失败样本形成接入记录；不可用就更换合规方案，不预先承诺平台 |
| R1 · 证据与只读研究 | 模型/迁移、ContentPort、Fake、预算/任务/取消、来源卡片与安全边界 | 断网完整走通发现候选；权限与恶意来源测试通过，不产生行程写入 |
| R2 · 提案衔接 | 保存灵感、字段级来源引用、真实 ID 两步流程、过时检查、确认执行 | 采纳链路与既有流程回归通过；只对影响范围内操作，失败项可见 |
| R3 · 首个真实来源 | 在 R0 记录允许的配置下接入并端到端验收 | 通过 AC-18 后才开放真实联网；仍保留手动与 Fake 降级 |
| 后续 · 可选平台 | 小红书增强，点评/美团按各自验证结果接入 | 每个平台单独验收；不以已接通某一平台推断其他平台可用 |

本轮不安装组件、不修改环境配置、不调用真实模型或平台、不变更现有业务/页面代码，也不提交 Git。选择具体搜索服务、授权及费用上限是在 R0 中完成的实施前决策；本设计不要求现在提供任何密钥。
