# FairMeet 分阶段实施计划与验收策略

> 文档编号：05（计划集）
> 适用范围：FairMeet 完整出行规划产品
> 上游依据：`docs/deepseek-harness-implementation-brief.md`（下称"任务书"），重点第 6、9、11 节
> 性质：工程顺序与验收安排。**阶段只是工程排期，不代表产品定位收缩**；主线始终是"完整出行规划"，约饭/会面点/路线计算均为旅程内可复用子能力。
> 状态：**阶段 A 已获用户确认（2026-11-11）**，确认口径见 [07 · 已确认决策记录](07-confirmed-decisions.md)。可按 A–E 逐阶段推进；每阶段验收后再进入下一阶段。

---

## 0. 阅读约定

- **每阶段只做一个可验证闭环**：一次只完成一个阶段，不并行铺开大量未闭环页面与空接口（任务书 §11.4）。
- **DoD（Definition of Done）**：阶段退出标准，须可演示、可测试、可复现，不以"编译通过/能调 LLM"冒充验收（任务书 §8、§9 末段）。
- **断网/降级可测**：所有涉及外部服务的验收项都必须能在 mock 网络下跑（`respx` 拦截 httpx）；真实网络仅作补充演示。
- **"明确不做"** 是防烂尾围栏，阶段内不得越界，越界需求记入下一阶段或待办。
- 交接模板见第 6 节，每阶段结束必须填写。

## 1. 阶段 A–E 表格化计划

### 阶段 A — 产品与工程基线（=当前这轮）

| 项 | 内容 |
|----|------|
| **目标** | 只读盘点仓库，产出可审阅的架构、数据模型、用户流程、技术与阶段计划、风险与验收策略；**不写业务代码**，等用户确认。 |
| **交付物** | 本计划集文档：目标架构、旅程数据模型草案、端到端用户流程、阶段计划（本文）、技术选型理由、风险清单、验收策略；旧会面点规格→旅程子能力的迁移说明。 |
| **涉及模块/文件** | 只读：`fairmeet/center.py`、`fairmeet/geocode.py`、`fairmeet/config.py`、`tests/*`、`README.md`、`docs/phase0-spec.md`、`.env` / `.env.example`；产出：`docs/plan/*.md`。 |
| **前置依赖** | 无。需先核对当前未提交/未跟踪改动并原样保护（任务书 §11.1）。 |
| **可验证闭环** | 文档可被用户逐节审阅；盘点结论与实际代码一致（现有：无应用入口、无前端、无持久化，仅球面中心 + 高德地理编码 + 配置读取 + 单元测试）。 |
| **退出标准 (DoD)** | ① 架构/数据模型/流程/阶段/风险/验收文档齐备且互相一致；② 旧规格迁移路径明确；③ 给出技术选型理由（是否沿用 FastAPI、前端方案）；④ 用户明确确认计划；⑤ 仓库业务代码零改动。 |
| **明确不做** | 不写 API、不写前端、不建数据库、不接 LLM、不安装依赖、不 git 提交/推送。 |

### 阶段 B — 旅程协作基础

| 项 | 内容 |
|----|------|
| **目标** | 打通"创建旅程→邀请成员→成员录入需求→放灵感→手动加地点"的协作主流程，**无外部解析服务也能走完**。 |
| **交付物** | 应用入口（FastAPI + uvicorn）、持久化模型与迁移、旅程/成员 REST 接口、移动端适配的旅程空间页、邀请链接加入流程、成员需求录入与状态展示（硬约束/偏好/可协商）、灵感箱 + 手动添加地点、灵感状态机。 |
| **涉及模块/文件** | 新增：`fairmeet/app.py`（入口/路由装配）、`fairmeet/models/`（SQLModel/pydantic 领域模型：Trip/Member/Need/Inspiration/Place）、`fairmeet/api/trips.py`、`members.py`、`inspirations.py`、`fairmeet/db.py`、`fairmeet/templates/`、`fairmeet/static/`；沿用：`config.py`。 |
| **前置依赖** | 阶段 A 获用户确认。 |
| **可验证闭环** | 以**成都 3–5 人 / 2–3 天国内游**为验收场景：发起人创建旅程→生成不可猜的邀请链接→第二名成员从手机浏览器打开并加入→提交一条硬约束与一条偏好→两人各加一条灵感/地点（手动添加或粘贴链接+描述）→所有人看到一致状态；全程**不调用任何外部解析、不调用高德**即可完成。 |
| **退出标准 (DoD)** | ① 旅程/成员/需求/灵感 CRUD 有接口且有自动化测试；② 邀请链接鉴权：未授权者不能访问他旅程；③ 成员需求可标记硬约束/偏好/可协商并显示回应状态；④ 灵感可手动添加地点、可改状态（已识别/待确认/解析失败等）；⑤ 移动端浏览器可完成加入与录入；⑥ 关键测试 mock 网络、断网可跑；⑦ 无真实密钥入库。 |
| **明确不做** | 不做逐日行程编辑、不做地图、不做路线、不做 AI 对话、不做链接自动解析（失败手动补）。 |

### 阶段 C — 可编辑计划与地图

| 项 | 内容 |
|----|------|
| **目标** | 建立可编辑逐日行程，并把地图/时间线、约束检查、预算汇总、餐饮与会面点作为旅程内能力接入。 |
| **交付物** | 逐日行程条目（日期/时间/活动/地点/停留/交通段/费用/来源/确认状态）、草案↔待讨论↔待确认↔已确认状态流转、时间线与地图联动、地理编码/POI/路线**适配层**（接口+高德实现+mock 实现）、约束检查、预算汇总、行程校验、餐饮与会面点作为行程条目。 |
| **涉及模块/文件** | 新增：`fairmeet/models/itinerary.py`（Day/Item/TransportSegment）、`fairmeet/api/itinerary.py`、`fairmeet/services/geo_adapter.py`（地理编码/POI/路线统一接口）、`fairmeet/services/checks.py`（约束/预算/校验）、`fairmeet/services/meetpoints.py`（复用 `center.py` 作旅程内会面点能力）、行程编辑页与地图页模板。 |
| **前置依赖** | 阶段 B 完成（旅程/成员/地点已持久化）。 |
| **可验证闭环** | 在一个多日旅程里排 2 天行程、每项挂地点与交通段、在地图看到点与连线、切换某天时间线高亮对应地图点；跑一次约束检查与预算汇总得到可解释结果；把一家餐厅和一个会面点作为行程条目加入并显示。 |
| **退出标准 (DoD)** | ① 行程条目字段完整、状态流转有测试；② 地图与时间线联动可用；③ 适配层对"外部不可用"有明确降级（返回估算/未知标记，不崩）；④ 约束检查能报出硬约束冲突且**不自动放宽**；⑤ 预算/交通数值标明来源或"估算"（不得 LLM 编造精确数）；⑥ 餐饮/会面点以行程条目形态存在，不另起独立流程；⑦ 适配层与检查逻辑单测 mock 网络、断网可跑。 |
| **明确不做** | 不做 AI 对话式协调、不做自动多源解析、不做实时协作推送、不做导出/离线。 |

### 阶段 D — AI 协调与来源增强

| 项 | 内容 |
|----|------|
| **目标** | **先**结构化输入输出 + 受控业务工具 + 校验，**再**对话式协调；数据源逐个接入并记录可用性与降级。 |
| **交付物** | AI 结构化 I/O 契约（JSON Schema 校验）、受控业务工具层（AI 只能通过校验过的 operation 提案，不能直写库）、对话式协调：需求追问/灵感整理/冲突解释/方案比较/局部修改提案；数据源适配器逐个接入 + 可用性台账 + 降级策略；来源/推断/核实状态/操作影响标示。 |
| **涉及模块/文件** | 新增：`fairmeet/ai/contracts.py`（输入输出 schema）、`fairmeet/ai/tools.py`（受控工具，包装 services）、`fairmeet/ai/orchestrator.py`（对话编排）、`fairmeet/ai/validators.py`、`fairmeet/sources/`（各数据源 adapter + registry/可用性记录）；接入点复用阶段 C 的 services。 |
| **前置依赖** | 阶段 C 完成（行程与适配层稳定、有确定性服务可供 AI 调用）。 |
| **可验证闭环** | 用户自然语言提出"把第二天下午改轻松点"→ AI 输出结构化修改提案→校验器通过→展示受影响项差异→用户确认后调用受控工具落库；某数据源 mock 为不可用时，界面显示"降级/已用估算"而非报错。 |
| **退出标准 (DoD)** | ① AI 输出必须通过 JSON Schema 校验，未通过不落库；② AI 不得绕过权限/直写数据库（测试断言只经 tools）；③ 冲突解释引用真实约束数据，不编造；④ 修改提案展示影响范围并等待确认；⑤ 每个接入数据源有可用性记录与降级路径；⑥ 来源/推断/核实状态可见；⑦ LLM 相关测试用假响应/mock，断网可跑。 |
| **明确不做** | 不把未经验证抓取当生产依赖、不做交易/支付、不做多 Agent 框架大改。 |

### 阶段 E — 出发前与途中体验

| 项 | 内容 |
|----|------|
| **目标** | 完善确认、变更历史、通知、出发前摘要与移动端途中查看；验证局部重排保留未受影响确认项并清楚展示差异。 |
| **交付物** | 计划确认流程、变更历史/版本、重要更新通知（先普通请求/刷新即可）、出发前摘要视图、移动端途中查看；局部重排（针对某天/局部）保留其他已确认项并展示差异与受影响路线/预算；据反馈**再评估**导出/离线/外部预订（仅评估，不默认实现）。 |
| **涉及模块/文件** | 新增：`fairmeet/services/changes.py`（变更记录/审计）、`fairmeet/api/history.py`、通知模块、`fairmeet/templates/summary`、途中视图；复用阶段 B–D。 |
| **前置依赖** | 阶段 D 完成。 |
| **可验证闭环** | 确认一份计划→发起某天局部重排→系统只改受影响项、保留其他已确认项、并列出差异→历史里可看到变更前后→移动端能查看出发前摘要与途中某天。 |
| **退出标准 (DoD)** | ① 已确认项修改必须展示差异并二次确认；② 局部重排不无故覆盖其他已确认安排（有回归测试）；③ 变更历史可读可追溯；④ 通知/刷新可见更新；⑤ 出发前摘要与途中查看在移动端可用；⑥ 导出/离线/外部预订以评估结论呈现，未擅自实现。 |
| **明确不做** | 不默认实现导出/离线/外部预订交易；不引入 WebSocket/Redis 等，除非有实测需求依据。 |

## 2. 阶段间依赖图与关键路径

```
                 ┌─────────────────────────────────────────────┐
                 │ 阶段 A  产品与工程基线（只读盘点+文档，待确认）│
                 └───────────────────────┬─────────────────────┘
                                         │ 用户确认
                                         ▼
                 ┌─────────────────────────────────────────────┐
                 │ 阶段 B  旅程协作基础                          │
                 │ (入口/持久化/旅程成员/需求/灵感箱)            │
                 └───────────────────────┬─────────────────────┘
                                         │ 旅程·成员·地点已持久化
                                         ▼
                 ┌─────────────────────────────────────────────┐
                 │ 阶段 C  可编辑计划与地图                      │
                 │ (逐日行程/地图时间线/适配层/检查/预算/餐饮会面点)│
                 └───────────────────────┬─────────────────────┘
                                         │ 行程+确定性服务+适配层稳定
                                         ▼
                 ┌─────────────────────────────────────────────┐
                 │ 阶段 D  AI 协调与来源增强                     │
                 │ (结构化IO/受控工具/对话/数据源+降级/来源标示)   │
                 └───────────────────────┬─────────────────────┘
                                         │ 提案-校验-确认 通路就绪
                                         ▼
                 ┌─────────────────────────────────────────────┐
                 │ 阶段 E  出发前与途中体验                      │
                 │ (确认/变更历史/通知/摘要/途中/局部重排差异)    │
                 └─────────────────────────────────────────────┘
```

**关键路径**：A → B → C → D → E（严格串行，后一阶段依赖前一阶段闭环）。

- **A→B 门**：用户确认计划（硬门，不可跳过）。
- **B→C 门**：旅程/成员/地点持久化接口通过测试。
- **C→D 门**：确定性服务（约束检查、预算、路线适配层）具备稳定接口——AI 只能调用工具，故 C 的 service 契约先冻结。
- **D→E 门**：AI 修改提案（提案→校验→确认→落库）通路可用，E 的变更历史与差异展示依赖它。

**可并行点**（同阶段内）：C 中"地图适配层"与"约束/预算服务"可分属不同文件并行；D 中"结构化契约"与"数据源台账"可分头推进。但**跨阶段不并行**，避免多阶段半成品叠加。

3. 密钥扫描：仓库内无真实 key（仅 `.env.example` 占位）。
4. 新环境按 README 步骤能启动并跑测试（阶段 B 起建立启动说明）。

**阶段内"验收剧本"演进**：

- C 阶段：剧本 #4（确定性口径）、#5、#6。
- D 阶段：剧本 #4（AI 口径）、#7（AI 修改提案）。
- E 阶段：剧本 #7（完整确认/差异）、#8。
- 阶段 E 收尾做一次全剧本 #1–#10 端到端走查，作为整体收敛验收。

## 4. 依赖与工具清单（分层 requirements 说明，**不实际安装**）

当前仓库已有：`python-dotenv`（`config.py` 使用）、`pytest`、`respx`（测试用，见 phase0-spec）、httpx（规格技术栈）。阶段推进建议采用**分层 requirements**，运行与开发分离，避免把测试/工具依赖塞进生产环境。

建议结构（示意，不在本阶段安装）：

| 文件 | 层 | 内容（建议） | 谁需要 |
|------|----|--------------|--------|
| `requirements.txt` | 运行（基础） | `fastapi`、`pydantic>=2`（pydantic v2）、`uvicorn[standard]`、`jinja2`（服务端模板）、`httpx`、`python-dotenv`、`SQLModel` 或 `sqlalchemy` + 驱动（阶段 B 定，见下） | 生产运行时 |
| `requirements-dev.txt` | 开发/测试 | `-r requirements.txt`、`pytest`、`pytest-asyncio`、`respx`（mock httpx）、`ruff` | 开发者/CI |
| （可选）`requirements-ai.txt` | 运行增强（阶段 D） | LLM 客户端 SDK、JSON Schema 校验库（如 `jsonschema`） | 仅启用 AI 时 |

要点说明：
- **fastapi**：沿用现有 Python 骨架并复用已有 `httpx` 习惯；模块化单体足够（任务书 §7），不拆微服务。
- **pydantic v2**：数据模型与 AI 结构化 I/O 校验的基础。
- **uvicorn**：ASGI 运行入口（阶段 B 应用入口）。
- **jinja2**：移动端友好、可分享链接的轻量服务端渲染，避免早期上重前端框架。
- **持久化**：阶段 B 再定 `SQLModel`（pydantic 友好、上手快）或 `SQLAlchemy` + SQLite；**早期只用 SQLite，不引 Redis/Postgres**（任务书 §7）。
- **ruff**：已在规格中要求，作为 lint 门禁。
- **respx / pytest-asyncio**：保证"断网可测、mock 网络"的验收要求。
- **版本锁定**：建议同时产出 `requirements.lock` 或 `constraints.txt` 以保证新环境可复现（阶段 B 建立）。

> 注：本节只给方案与分层理由，**不在阶段 A 安装任何依赖**；实际 `pip install` 归入阶段 B 起步。
