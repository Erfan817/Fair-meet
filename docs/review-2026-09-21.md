## 2. 总体路线：三段式，不要跳步

```text
先完成确定性推荐系统
    ↓
再增加通勤时间公平算法
    ↓
最后接入 Agent 处理自然语言需求
```

**为什么不能先接 Agent**：如果现在直接接 LLM，容易退化成

```text
用户输入 → LLM → 调几个函数 → 返回结果
```

看起来像 Agent，但项目的核心业务能力并没有建立起来，简历上也不够有说服力。

## 3. 第一阶段：先把 Phase 0 跑通

### 3.1 完成配置模块

让 `config.py` 集中管理，且全部来自环境变量，**不写死在代码里**（`.env.example` 的方向是对的）：

| 配置项 | 说明 |
|--------|------|
| 高德 Web 服务 Key | 服务端 REST：地理编码、周边搜索 |
| 高德地图 JS Key | 前端地图展示（Day 8~9 才用） |
| 地理编码接口地址 | 便于替换 / mock |
| POI 搜索接口地址 | 同上 |
| 请求超时时间 | |
| 最大并发数 | 对应 `asyncio.Semaphore` |
| 搜索半径 | 默认 1500m（规格 FR-4） |
| Top N 数量 | 默认 5，上限 10（规格 FR-5） |
| 各评分因子权重 | 改配置即可调权重，不动代码 |

### 3.2 把高德地理编码封装成正式模块

建议的职责划分：

```text
Geocoder
├── geocode(address)
├── geocode_many(addresses)
├── 失败处理
├── 超时处理
├── 并发限制
└── 进程内缓存
```

这里重点体现的工程能力：

- `httpx.AsyncClient`
- `asyncio.gather` 并发
- `asyncio.Semaphore` 限流（高德有 QPS 限制）
- 超时与网络异常处理
- 同一地址避免重复请求（进程内缓存）
- **无效地址单独记录，而不是让整个请求失败**（规格 FR-2 的部分降级）

输入：

```json
{ "locations": ["北京大学", "五道口", "这是一个不存在的地方"] }
```

期望输出：

```json
{
  "valid_locations": ["北京大学", "五道口"],
  "dropped_locations": ["这是一个不存在的地方"]
}
```

### 3.3 把 `geocode_test.py` 改成正式 Mock 测试

原脚本（根目录手工验证脚本）的问题：

- 文件名不是 `test_*.py`，不会被 pytest 发现
- 会真实访问网络
- 直接读取 `AMAP_WEB_KEY`
- 没有断言
- 失败时异常信息不明确

目标测试结构：

```text
tests/
├── test_center.py
├── test_geocode.py
├── test_poi.py
└── test_scoring.py
```

用 `respx` 拦截 HTTP 请求，确保 **`pytest` 在断网时也能通过**。

> 这是一个非常适合写进简历的工程细节：说明你不是只会调 API，而是考虑了测试隔离、第三方服务 Mock、API 配额、可重复测试、异常场景。

### 3.4 实现 POI 搜索和评分

这是项目从「算法练习」变成「完整应用」的关键一步。把搜索和评分拆开：

```text
fairmeet/
├── center.py
├── geocode.py
├── poi.py
├── scoring.py
├── config.py
└── models.py
```

确定性的多因子评分模型：

```text
总分 = 距离分 × distance_weight
     + 热度分 × popularity_weight
     + 关键词匹配分 × keyword_weight
```

每个候选地点返回分数明细：

```json
{
  "name": "示例咖啡厅",
  "score": 86.5,
  "score_detail": { "distance": 32.0, "popularity": 28.5, "keyword": 26.0 }
}
```

> 「可解释评分」是 FairMeet 很好的特色，应该保留。

### 3.5 实现 FastAPI 接口

先只实现一个：

```text
POST /api/v1/recommend
```

调用链：

```text
请求参数校验 → 批量地理编码 → 过滤无效地点 → 计算公平中心
→ 搜索周边 POI → 评分排序 → 返回推荐结果
```

**为每一层定义清晰的数据模型，不要在接口函数里堆大量字典**：

```text
RecommendRequest / GeocodedLocation / Venue / ScoreDetail / RecommendResponse
```

这样后续接入 Agent 时，工具的输入输出也会更稳定。

## 4. 第二阶段：把「地理中心」升级成真正的「公平中心」

球面几何中心作为 Phase 0 很合理，但它**不一定代表真实的公平性**：

- 一个人住在地铁线上，一个人住在偏远区域
- 两个人直线距离差不多，但实际通勤时间可能相差很大

Phase 1 的算法链路：

```text
地理中心 → 候选会面点生成 → 查询每个人到候选点的通勤时间
→ 最小化通勤时间方差 → 输出公平性更高的地点
```

公平目标函数：

```text
公平成本 = 通勤时间平均值 + λ × 通勤时间方差
```

这样项目就从普通的「地图中点推荐」升级为：

> **面向多人通勤成本优化的公平会面点推荐系统**

### 球面中心算法待补的边界情况

> **风险点**：当输入点接近**对跖点**时，三维向量之和可能接近零，此时中心点在数学上不稳定。

待补测试与策略：

- [ ] 跨 180° 经线测试
- [ ] 高纬度测试
- [ ] 重合点测试
- [ ] 近对跖点测试
- [ ] 向量模长过小时的错误处理策略

## 5. 第三阶段：再接入 Agent

Phase 2 的路线图设计得比较好。**Agent 不应该负责「计算中心点」**，而应该负责：

- 理解用户自然语言
- 提取参与者位置
- 提取场所偏好
- 识别约束条件
- 调用推荐工具
- 根据反馈重新排序
- 解释推荐理由

例：

> 我、在望京的朋友和住五道口的朋友，想找一个安静、离地铁近、适合聊天的咖啡厅。

解析为：

```json
{
  "locations": ["我所在的位置", "望京", "五道口"],
  "keyword": "咖啡厅",
  "requirements": ["安静", "离地铁近", "适合聊天"]
}
```

然后调用确定性的推荐服务。

### 推荐架构

```text
用户
 ↓
FairMeet Agent
 ├── 位置解析工具
 ├── 公平中心推荐工具
 ├── 条件筛选工具
 ├── 结果解释工具
 └── 重新排序工具
 ↓
FairMeet Core
 ├── Geocoder
 ├── Fair Center
 ├── POI Search
 └── Scoring
```

技术选型参考：LangGraph（对话状态与条件路由）、Function Calling（调用业务工具）、FastAPI、Pydantic、Redis（缓存地理编码与 POI）、PostgreSQL / SQLite（会话与推荐记录）。

> ⚠️ **原则**：Agent 层应该调用业务模块，**而不是把业务逻辑全部塞进 Prompt**。

## 6. 简历包装

**项目名**：FairMeet：基于通勤公平性的多智能体会面点推荐系统

**描述**：

```text
设计并实现多人公平会面点推荐系统，基于高德地图 API 完成地址解析、球面中心计算、
周边 POI 检索和多因子可解释排序；使用 FastAPI 暴露推荐服务，通过 asyncio + Semaphore
实现批量地理编码并发控制，并使用 respx 对第三方 HTTP 请求进行隔离测试。后续基于
LangGraph 接入对话式 Agent，支持用户通过自然语言动态调整地点、距离、地铁和场所类型等推荐条件。
```

```text
- 支持无效地址部分降级
- 推荐结果返回可解释分数明细
- 测试覆盖率达到 XX%
```
