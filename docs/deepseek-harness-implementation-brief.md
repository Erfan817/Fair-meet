# FairMeet 完整出行规划产品实施任务书

> 用途：交给 DeepSeek Harness，作为产品方向与工程实施主任务书。
> 产品主线：完整出行规划。多人约饭与会面点推荐均是旅程中的子能力，不是产品定位或独立 MVP。
> 实施原则：先盘点当前仓库和工作区，再给出计划；经用户确认后分阶段实现。

## 1. 总任务

将 FairMeet 逐步发展为一个由 AI 协助、同行者共同参与的出行规划产品。它把成员分散的灵感、个人需求和现实约束，整理成有来源、可讨论、可执行，并能随变化局部调整的共享旅程计划。

产品围绕“一趟旅程”组织数据和交互。聊天是创建、询问和修改计划的入口；旅程空间、逐日行程、地图和协作状态才是计划本身。不要只生成一篇不可协作、不可编辑的攻略文本。

## 2. 必须遵守的产品边界

1. 主线始终是完整出行规划，覆盖创建旅程、邀请成员、收集灵感、协调需求、共同形成计划、检查、确认和途中调整。
2. 餐厅推荐、多人约饭、会面点推荐、路线计算和地点发现都是旅程内可复用的子功能；不得把其中任何一项重新定义成产品主线或唯一 MVP。
3. 可以控制首轮交付的场景和实现规模，但要验证完整旅程的端到端主链路；分阶段实施不等于缩小产品定位。
4. AI 负责理解、追问、整理、提出方案和解释取舍；成员保留最终决策权。不得静默修改已确认计划。
5. 明确区分硬约束、偏好和可协商项。硬约束冲突时必须显式报告并请成员处理，不得由模型擅自忽略。
6. 重要内容保留来源、核实状态和不确定性。不得把模型推断伪装成已核实事实。
7. 不假设任何社交平台链接都能稳定解析。导入失败时允许手动补充或修正，不能阻塞规划。
8. 订票、支付和订单履约不属于本任务核心范围，可外链或预留接口，不要擅自实现交易系统。

## 3. 端到端用户流程

### 3.1 创建旅程

用户通过自然语言或表单描述目的地、日期、同行者、预算和旅行偏好。AI 提取已知字段，对影响规划的关键缺项追问；用户能检查和修改提取结果。产物是可持续编辑的旅程草案。

### 3.2 邀请同行者与收集需求

发起人通过分享链接邀请成员。成员提交和更新出发地、可参加日期、预算、兴趣、饮食及行动/无障碍需求。每项需求标记为硬约束、偏好或可协商项。显示加入状态、未回应项和待补充信息，并实施成员访问权限。

### 3.3 收集灵感与来源

成员将链接、地点、攻略文字或手动记录放入旅程灵感箱。系统尝试抽取地点、活动、时间建议和来源，进行去重、分类及具体地点/分店匹配。状态包括已识别、待确认、已核实、解析失败或已排除。失败后可手动修正。

### 3.4 汇总约束与发现冲突

系统汇总日期、预算、成员偏好、出发地和硬约束，提示日期冲突、预算超限、地点过多、行动需求不匹配等问题。AI 可以总结待讨论问题和提出选项，不得自动放宽硬约束。

### 3.5 形成并比较方案

AI 基于灵感、约束、地点和路线数据产生一个或多个可比较方案。方案可在目的地安排、住宿区域、每日主题、活动密度、预算或交通方式上体现不同取舍。展示依据、预算估算、交通影响、主要取舍和未核实信息。

### 3.6 共同编辑逐日行程

成员在共享计划中查看和编辑每日安排。行程条目表达日期/时间、活动、地点、预计停留、交通段、费用估算、来源和确认状态。地图与时间线关联；成员可评论、收藏备选、投票、提出替换或确认。

### 3.7 检查可执行性

系统检查时间安排、地点间交通、营业时间（若可用）、预算、行程密度和明显绕行。数据需区分已核实、外部数据、估算和未知。路线与数值须来自地图/规则服务或明确标为估算，不能由 LLM 凭空给精确数字。

### 3.8 确认、出发前查看与途中调整

计划项支持草案、待讨论、待确认、已确认、已完成、已取消/替换等状态。修改已确认内容时，展示差异及受影响的路线、预算和后续安排，用户确认后才更新。旅途中可针对某天或局部安排重排，尽量保留不受影响的已确认项。

## 4. 功能模块

1. **旅程空间**：基本信息、成员、共享权限、旅程状态。
2. **成员与需求**：加入、硬约束/偏好/可协商项、回应状态。
3. **灵感箱与来源**：链接/文字/地点导入、解析、去重、人工修正、来源和核实状态。
4. **地点库**：统一地点与分店、坐标、类别、外部来源映射及重复项合并。
5. **方案比较**：候选安排及预算、节奏、路线和成员影响差异。
6. **行程编辑器**：按天组织活动、地点、餐饮、住宿和交通，支持局部调整。
7. **地图与路线**：展示地点和路线、交通时间与成员负担；数据不可用时明确降级。
8. **协作决策**：评论、投票、待确认、成员确认和变更记录。
9. **AI 协调助手**：自然语言输入、澄清、冲突总结、方案生成、解释和受控修改。
10. **行程检查与预算**：确定性校验、费用汇总、估算和风险提示。
11. **通知与变更**：重要更新、受影响成员、差异及历史。
12. **行程摘要与导出**：出发前摘要及适合分享/执行的视图。

餐厅、集合点和会面地点通过地点库与行程能力按需调用，不形成与旅程割裂的产品流程。

## 5. AI 与系统职责

**AI 负责：** 解析自然语言并让用户确认关键字段；总结成员需求、发现冲突；整理灵感并抽取候选地点；基于系统提供的数据提出方案；生成计划修改提案。对已确认安排的修改必须展示影响并等待确认。

**系统/业务服务负责：** 持久化旅程和成员权限；地点规范化、地理编码、POI 与路线查询；硬约束校验、路线/时间/预算计算、状态流转和变更审计；记录外部数据来源、获取时间和状态；输入校验、权限、成本保护和错误处理。

AI 不得绕过权限或直接写数据库；应通过经过校验的业务操作提出修改。遇到冲突、外部数据不确定或信息不足时，明确询问或标注，禁止编造。

## 6. 建议的实施阶段

阶段仅代表工程顺序，不代表产品定位收缩。Harness 应先检查仓库与当前未提交改动，随后提交细化计划、依赖和风险；经用户确认后实施。

### 阶段 A：产品与工程基线

- 只读盘点代码、文档、测试、依赖、未提交改动和密钥配置；保护所有既有变更。
- 说明旧会面点推荐规格如何转为旅程中的可复用能力。
- 提交目标架构、旅程数据模型草案、用户流程、阶段计划、技术选型理由、风险和验收策略；大规模编码前等待用户确认。

### 阶段 B：旅程协作基础

- 建立应用入口、持久化模型和旅程/成员接口。
- 提供移动端适配的旅程空间、邀请加入、成员需求录入和状态展示。
- 建立灵感箱及手动添加地点的能力，无外部解析服务也能继续主流程。

### 阶段 C：可编辑计划与地图

- 建立逐日行程、地点、交通段和草案/确认状态。
- 实现时间线与地图联动、地点搜索/地理编码/路线适配层。
- 提供约束检查、预算汇总和行程校验。
- 将餐饮和会面点作为旅程内能力接入，不改变产品主线。

### 阶段 D：AI 协调与来源增强

- 先实现结构化输入输出、受控业务工具和校验，再提供对话式协调。
- 支持需求追问、灵感整理、冲突解释、方案比较和局部修改。
- 逐个接入合法且稳定的数据源；记录可用性和降级方式，不将未经验证的抓取作为生产依赖。
- 标示来源、推断、核实状态及操作影响。

### 阶段 E：出发前与途中体验

- 完善计划确认、变更历史、通知、出发前摘要和移动端途中查看。
- 验证局部重排保留未受影响的确认项，并清楚展示差异。
- 根据实际反馈再评估导出、离线或外部预订整合。

## 7. 架构指导

- 优先模块化单体，职责清晰，不在早期拆微服务。
- 当前仓库是 Python 小型项目；先核实依赖与约定，再决定是否沿用 FastAPI。前端应支持通过邀请链接在手机浏览器使用，技术选型需说明理由。
- 领域模型与地图、内容、AI 提供方解耦；外部格式不得渗入核心行程模型。
- API、业务逻辑和外部适配器分别测试；关键测试 mock 网络并可离线运行。
- 密钥仅从环境或安全配置读取，不写入仓库或日志。
- 先完成单旅程端到端协作，再按需求引入异步任务、缓存和通知基础设施。无实际需求或测量依据时，不预先引入 Redis、微服务或复杂 Agent 框架。
- 保存重要计划变更历史/版本，支持理解和恢复修改。

## 8. 非功能要求

- 移动端优先，关键协作可从分享链接完成。
- 成员仅能访问授权旅程；退出、删除和隐私设置行为明确。
- 最小化收集个人数据，谨慎处理位置、健康/饮食和行动需求。
- 外部服务超时、限流或无结果时提供可理解错误和手动降级路径。
- 记录 AI 修改提案、用户确认和数据来源；日志不得泄露密钥或无关敏感信息。
- 重要业务规则有自动化测试，并提供本地启动与配置说明。
- 不以“能调用 LLM”作为验收；验证计划结构、约束、来源状态和修改范围符合请求。

## 9. 完成标准

使用一趟多人、多日旅程作为端到端验收场景：

1. 发起人创建旅程并邀请至少一名同行者。
2. 成员提交不同偏好和至少一项硬约束。
3. 多名成员添加灵感；系统保留来源，并支持确认或手动修正识别结果。
4. 系统呈现冲突或缺失信息，用户能处理，AI 不会静默跳过。
5. 生成可编辑逐日计划，地点可在地图查看，餐饮和集合点也作为行程项目处理。
6. 交通/预算显示数据来源或估算状态，硬约束有规则校验。
7. 成员可讨论和确认；修改已确认项会展示差异并要求确认。
8. 局部调整不会无故覆盖其他已确认安排。
9. 外部 API 不可用时有明确降级方式，关键测试可离线运行。
10. 新环境能按文档配置、启动和测试，仓库无真实密钥。

每阶段结束提交改动摘要、设计决定、运行方式、测试真实结果、已知限制、未实现项及下一阶段建议。不得声称未运行的测试通过，也不能以编译成功代替产品验收。

## 10. 风险与待验证事项

- 小红书、大众点评及社交媒体链接的访问和解析可能变化；先验证合法性、稳定性和维护成本，再决定是否集成。
- 地图平台的路线、POI、配额、密钥类型及中国境内坐标体系须按实际 API 文档确认。
- 交通、营业信息、价格和用户内容会过期，显示数据时间或不确定状态。
- 用硬约束校验、结构化输出、操作前确认和回归测试降低 AI 漏项风险。
- 共享旅程包含个人偏好和位置，明确可见范围、最小化收集和删除策略。
- 实时协作可先用普通请求/刷新验证流程，确认需要后再采用 WebSocket 等机制。

## 11. Harness 执行协议

1. 首先只读检查仓库和工作区，尤其保护已有未提交文件；报告实际代码与本文目标的差异。
2. 将本文视为产品方向和边界，不视为要求一次性实现所有模块的单轮编码任务。
3. 先提交可审阅的架构、数据模型、分阶段计划、每阶段验收和风险；不得擅自把主线改回约饭或会面点推荐。
4. 用户确认计划后，每次完成一个可验证阶段，不同时铺大量未闭环页面和空接口。
5. 修改范围保持清晰；不得覆盖既有改动；说明新依赖、外部服务和配置要求。
6. 运行对应测试并如实报告；未运行或受凭证限制的部分明确说明。
7. 未经用户明确要求，不提交、推送、发布或向外部平台发送内容。

## 12. 当前仓库背景（仅供启动盘点）

此前只读盘点显示项目为 Python 小型仓库，有球面中心计算和高德地理编码雏形；未发现完整应用 API、前端、地点搜索闭环或持久化。README 和旧规格仍以会面点推荐为主。工作区曾存在未提交/未跟踪改动，因此 Harness 必须重新检查当前状态，保留所有既有改动，不可假设历史盘点仍完全准确。
